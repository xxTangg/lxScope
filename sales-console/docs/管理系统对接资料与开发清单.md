# 龙信管理系统与新销售总台对接资料与开发清单

> 本文档用于发送给龙信管理系统（客户系统/管理中心）开发人员。请根据“需要对方提供”和“需要对方实现”两部分准备资料和代码，以便两个系统完成内网联调。

## 一、对接目标

管理系统与新销售总台通过稳定的 HTTP API 连接，不共享数据库，不读取旧销售总台的数据。

需要打通的业务包括：

1. 管理系统提交系统级充值申请。
2. 销售人员审批或拒绝充值申请。
3. 管理系统获取审批后的充值码并确认到账。
4. 管理系统定时上报客户系统整体额度和 Token 使用汇总。
5. 销售总台远程探测客户系统、执行升级并确认版本。

普通用户的个人申请先保留在管理系统内部。只有客户管理员审批后，因客户系统 Token 池不足而发起系统级充值申请时，销售总台才会收到数据。

## 二、双方数据流

```text
普通用户
   │ 在客户系统内提交申请
   ▼
客户管理中心 ──客户 Bearer Token──▶ 新销售总台 API ──▶ PostgreSQL
       ▲                                  │
       │ 轮询充值码、确认到账               │ 销售人员审批
       └──────────────────────────────────┘

销售人员在销售总台发起升级
   │
   ▼
客户管理系统 /integration/sales/v1/upgrades/*
   │ 下载升级包、备份、升级、重启、回滚
   ▼
客户管理系统 /integration/sales/v1/ping 返回新版本
```

## 三、请管理系统开发人员提供的资料

请尽量一次性提供以下内容。没有这些资料，接口可以写出来，但无法完成可靠联调。

### 1. 系统和环境信息

- [ ] 客户名称。
- [ ] 稳定且唯一的 `system_id`，说明是否会永久不变。
- [ ] 测试环境和生产环境的系统名称、版本号。
- [ ] 管理系统服务地址：协议、IP/域名、端口、基础路径。
- [ ] 销售总台能否从内网访问管理系统。
- [ ] 管理系统能否主动访问销售总台。
- [ ] 防火墙、网闸、代理、DNS、TLS 证书等网络限制。
- [ ] 管理系统部署方式：Docker、虚拟机、物理机或其他方式。
- [ ] 管理系统实际运行的端口、容器名或服务名。

推荐提供以下格式：

```text
环境：测试 / 生产
system_id：<唯一系统 ID>
系统地址：https://<内网域名>:<端口>
管理接口基础路径：https://<内网域名>:<端口>/integration/sales/v1
销售总台访问管理系统：可以 / 不可以
管理系统访问销售总台：可以 / 不可以

```

### 2. Token 和身份认证

- [ ] 客户系统调用销售总台时使用的 `apiToken`。
- [ ] Token 是否按每套客户系统独立生成。
- [ ] Token 保存位置和加密方式。
- [ ] Token 是否有有效期、轮换和撤销机制。
- [ ] 管理系统是否可以按以下格式发送请求：

```http
Authorization: Bearer <apiToken>
Content-Type: application/json
```

- [ ] 说明普通用户、客户管理员、销售人员三种角色在管理系统中的权限名称。
- [ ] 说明普通用户申请、管理员审批、系统余额不足之间的状态变化。
- [ ] 提供测试账号，但不要在普通聊天或代码仓库中发送生产密码和生产 Token。

注意：销售总台使用的是“客户系统 Token”，不是普通用户个人 Token。普通用户不直接调用销售总台。

### 3. 现有接口和数据字典

请提供管理系统现有接口的以下任一种资料：

- [ ] OpenAPI/Swagger 文件。
- [ ] Postman 集合。
- [ ] 接口文档和请求示例。
- [ ] 关键数据表或数据字典。

每个接口至少说明：

- 请求方法、路径、请求头和请求体。
- 成功返回格式。
- 失败返回格式和错误码。
- 是否幂等。
- 超时时间、重试规则和限流规则。
- 时间戳单位：本项目使用 13 位毫秒时间戳。
- 金额单位：人民币元，最多两位小数。
- Token 数量单位：整数。

### 4. 额度和使用量口径

请确认以下字段在管理系统中的准确含义和计算规则：

- `pool_tokens`：当前客户系统 Token 池剩余量。
- `total_recharged`：客户系统累计充值金额，单位为元。
- `cumulativeConsumed`：客户系统累计消耗 Token 数。
- `cumulativeCredits`：客户系统累计赠送 Token 数。
- `app_version`：龙信业务应用当前版本。
- `system_id`：客户系统唯一 ID。

同时请说明：

- [ ] 这些数字是否会因人工调整而回退。
- [ ] 上报频率，例如 5 分钟、15 分钟或 1 小时。
- [ ] 管理系统重启后是否能继续上报正确的累计值。
- [ ] Token 池不足的判断阈值。
- [ ] 金额和 Token 的换算规则是否由销售总台统一下发。

### 5. 充值码验签配置

销售总台签发的充值码使用签名保护，管理系统需要：

- [ ] 提供公钥配置入口或配置文件位置。
- [ ] 支持保存销售总台公钥。
- [ ] 能够校验充值码签名、`system_id`、订单号、金额、Token 数和有效时间。
- [ ] 能够通过订单号或 nonce 防止重复兑换。
- [ ] 提供公钥更新和轮换步骤。

销售总台只提供公钥，不会把充值签名私钥交给管理系统。

### 6. 升级和运行信息

请提供或确认：

- [ ] 管理系统当前的应用版本和 AgentScope 平台版本。
- [ ] 应用和平台的安装目录、数据目录、备份目录。
- [ ] 备份、停止、启动、重启和回滚命令。
- [ ] 升级失败时的恢复方式。
- [ ] 管理系统是否支持无外网环境下载本地升级包。
- [ ] 升级是否需要数据库迁移、配置迁移或停机窗口。
- [ ] 单次升级预计耗时。
- [ ] 升级期间允许的最大不可用时间。

## 四、管理系统必须实现的接口

### A. 管理系统调用销售总台

以下接口由新销售总台提供，管理系统需要编写客户端调用。

#### 1. 提交系统级充值申请

```http
POST {SALES_CENTER_BASE_URL}/api/v1/integration/recharge-requests
Authorization: Bearer <apiToken>
Content-Type: application/json
X-Request-ID: <请求 ID>
Idempotency-Key: <唯一幂等键>
```

请求示例：

```json
{
  "system_id": "customer-system-001",
  "amount": "1000.00",
  "note": "Token 池不足，申请补充系统额度",
  "requested_at": "2026-09-15T08:30:00Z"
}
```

其中 `note` 为可选字段，最多 300 个字符；省略 `note` 时销售总台按空备注处理。`system_id`、两位小数金额 `amount` 和带时区的 `requested_at` 必须保留。

成功返回：

```json
{
  "order_id": "充值订单 ID",
  "system_id": "customer-system-001",
  "status": "pending",
  "delivery_status": "not_delivered",
  "request_id": "请求链路 ID"
}
```

要求：

- 只有客户管理员触发系统余额不足流程后才能调用。
- `system_id` 必须与销售总台登记的客户 Token 匹配。
- 网络超时后重试时，必须使用相同的 `Idempotency-Key`，避免重复创建订单。

#### 2. 查询充值申请状态

管理系统刷新已提交申请时，使用只读接口同步 `pending`、`approved` 或 `rejected` 状态。每次最多查询 200 个本系统的订单 ID：

```http
GET {SALES_CENTER_BASE_URL}/api/v1/integration/recharge-requests/status?system_id=customer-system-001&order_ids=<order-id-1>,<order-id-2>
Authorization: Bearer <apiToken>
X-Request-ID: <请求 ID>
```

响应中的顶层 `request_id` 是本次查询的请求 ID；每个订单的 `request_id` 是提交该充值申请时的原始请求 ID。订单仅在当前 Token 对应的系统 ID 范围内返回。

```json
{
  "orders": [
    {
      "order_id": "充值订单 ID",
      "system_id": "customer-system-001",
      "amount": "1000.00",
      "status": "rejected",
      "delivery_status": "not_delivered",
      "created_at": "2026-09-15T08:30:00Z",
      "request_id": "提交申请时的请求 ID",
      "decision_reason": null
    }
  ],
  "total": 1,
  "request_id": "本次查询的请求 ID"
}
```

#### 3. 轮询已批准充值码

```http
GET {SALES_CENTER_BASE_URL}/api/v1/integration/recharge-requests/poll
Authorization: Bearer <apiToken>
X-Request-ID: <请求 ID>
Idempotency-Key: <唯一幂等键>
```

查询参数必须携带 `system_id`，例如：

```http
GET {SALES_CENTER_BASE_URL}/api/v1/integration/recharge-requests/poll?system_id=customer-system-001
```

没有新结果时返回：

```json
{
  "orders": [],
  "request_id": "req-example"
}
```

审批通过时返回：

```json
{
  "orders": [
    {
      "order_id": "充值订单 ID",
      "system_id": "customer-system-001",
      "amount": "1000.00",
      "tokens": 1000000,
      "status": "approved",
      "delivery_status": "not_delivered",
      "recharge_code": "LXRC2.<payload>.<signature>",
      "expires_at": "2026-09-15T09:35:00Z"
    }
  ],
  "request_id": "req-example"
}
```

管理系统拿到充值码后必须先验签，再检查 `system_id`、金额、Token 数、订单号和 nonce，验签通过后才能入账。

#### 4. 确认充值到账

```http
POST {SALES_CENTER_BASE_URL}/api/v1/integration/recharge-requests/{order_id}/ack
Authorization: Bearer <apiToken>
Content-Type: application/json
X-Request-ID: <请求 ID>
Idempotency-Key: <唯一幂等键>
```

请求体：

```json
{
  "operation_id": "本地操作 ID",
  "system_id": "customer-system-001",
  "redemption_operation_id": "本地兑换操作 ID",
  "ledger_id": "本地账本 ID"
}
```

充值码兑换并入账成功后调用。重复调用应安全返回，不得重复增加额度。

#### 4. 上报客户系统汇总

```http
POST {SALES_CENTER_BASE_URL}/api/v1/integration/usage-reports
Authorization: Bearer <apiToken>
Content-Type: application/json
Idempotency-Key: <唯一幂等键>
```

请求示例：

```json
{
  "system_id": "customer-system-001",
  "pool_tokens": 860000,
  "total_recharged": "1000.00",
  "cumulative_consumed": 140000,
  "cumulative_credits": 20000,
  "app_version": "3.0.3",
  "client_reported_at": "2026-09-15T08:30:00Z"
}
```

要求：

- 建议定时上报，并在管理系统启动后主动上报一次。
- `pool_tokens`、累计消耗和累计赠送必须为非负整数。
- `total_recharged` 是客户系统汇总快照，不是销售交易凭证。
- 销售总台目前展示客户系统汇总，不接收普通用户个人用量明细。

#### 5. 下载升级包

管理系统执行升级时，使用客户 Token 下载：

```http
GET {SALES_CENTER_BASE_URL}/api/v1/integration/releases/core/latest
Authorization: Bearer <apiToken>
```

```http
GET {SALES_CENTER_BASE_URL}/api/v1/integration/releases/app/latest
Authorization: Bearer <apiToken>
```

当前内部兼容字段与新前端名称的对应关系：

| 内部字段 | 前端显示名称          | 含义                    |
| -------- | --------------------- | ----------------------- |
| `core`   | AgentScope 平台升级包 | AgentScope 平台整体升级 |
| `app`    | 龙信业务应用升级包    | 龙信业务应用升级        |

管理系统开发时必须使用 canonical 的 `app/core`；其中 `core` 指 AgentScope 平台整体升级，升级包必须按 AgentScope 包路径提供必要文件。

#### 6. 可选：连接验证

```http
POST {SALES_CENTER_BASE_URL}/api/v1/integration/verify-connection
Authorization: Bearer <apiToken>
Idempotency-Key: <唯一幂等键>
```

用于检查管理系统访问销售总台、以及销售总台反向访问管理系统的结果。

### B. 销售总台调用管理系统

销售总台使用客户 Token 反向调用以下接口。管理系统需要提供这些接口，或者提供等价适配层。

#### 1. 探活和版本查询

```http
POST {CUSTOMER_SYSTEM_BASE_URL}/integration/sales/v1/ping
Authorization: Bearer <apiToken>
Content-Type: application/json
```

建议返回：

```json
{
  "ok": true,
  "system_name": "客户名称",
  "system_id": "customer-system-001",
  "app_version": "3.0.3",
  "core_version": "2.1.0",
  "checked_at": "2026-09-15T08:30:00Z",
  "request_id": "请求链路 ID",
  "status": "healthy"
}
```

其中 `app_version` 用于确认龙信业务应用升级，`core_version` 用于确认 AgentScope 平台升级。

#### 2. 执行龙信业务应用升级

```http
POST {CUSTOMER_SYSTEM_BASE_URL}/integration/sales/v1/upgrades/app
Authorization: Bearer <apiToken>
Content-Type: application/json
Idempotency-Key: <唯一幂等键>
```

#### 3. 执行 AgentScope 平台升级

```http
POST {CUSTOMER_SYSTEM_BASE_URL}/integration/sales/v1/upgrades/core
Authorization: Bearer <apiToken>
Content-Type: application/json
Idempotency-Key: <唯一幂等键>
```

升级接口建议立即返回任务已接收：

```json
{
  "ok": true,
  "operation_id": "升级任务 ID",
  "state": "pending",
  "request_id": "请求链路 ID"
}
```

接口收到请求后，管理系统需要完成：

1. 下载对应升级包。
2. 校验包类型、版本和 SHA-256。
3. 备份当前文件和必要数据。
4. 解包并执行升级。
5. 重启对应服务。
6. 健康检查。
7. 失败时回滚。
8. 让 `/integration/sales/v1/ping` 返回新的 `app_version` 或 `core_version`。

#### 4. 远程重置客户管理员密码

```http
POST {CUSTOMER_SYSTEM_BASE_URL}/integration/sales/v1/admin-password-resets
Authorization: Bearer <apiToken>
Content-Type: application/json
Idempotency-Key: <唯一幂等键>
```

请求示例：

```json
{
  "operation_id": "重置操作 ID",
  "username": "客户管理员账号",
  "new_password": "一次性新密码",
  "expires_at": "2026-09-15T09:00:00Z"
}
```

管理系统必须再次确认调用方具有远程管理权限，并记录审计日志。

## 五、状态和错误处理要求

### 1. 充值订单状态

```text
客户管理员提交 → pending
销售人员批准   → approved
客户系统轮询   → 获得 code
客户系统兑换   → ack
销售总台记录   → delivery_status=delivered
销售人员拒绝   → rejected
```

### 2. 必须处理的 HTTP 状态

| 状态码       | 含义                 | 管理系统处理方式                |
| ------------ | -------------------- | ------------------------------- |
| 200/201      | 成功                 | 处理返回数据                    |
| 400          | 参数或业务状态错误   | 记录原因，不盲目重试            |
| 401          | Token 无效           | 告警并暂停调用，不能循环重试    |
| 404          | 订单或升级包不存在   | 记录并等待人工处理              |
| 409          | 重复或状态冲突       | 按订单 ID 查询/重试，不重复入账 |
| 429          | 请求过多             | 按 `Retry-After` 或退避策略重试 |
| 5xx/网络超时 | 服务或网络暂时不可用 | 指数退避重试并记录告警          |

### 3. 安全要求

- 生产环境优先使用 HTTPS 和内网 CA 证书。
- Token 只放在服务端安全配置中，不能写入前端日志、普通业务日志或错误提示。
- 充值码必须验签后使用，不能只解析内容而不验签。
- 升级包必须校验类型、版本、SHA-256 和签名（如果发布包签名已启用）。
- 升级和充值操作要记录操作者、系统 ID、订单号、版本和时间。
- 不允许管理系统直接访问销售总台 PostgreSQL。
- 不允许销售总台直接读取管理系统数据库；双方只通过约定 API 通信。

## 六、联调验收清单

请管理系统开发人员逐项配合验证：

- [ ] 正确 Token 可以提交充值申请。
- [ ] 错误 Token 返回 401。
- [ ] 普通用户申请只出现在客户系统内部。
- [ ] 客户管理员审批并触发系统余额不足后，销售总台出现待审核申请。
- [ ] 销售人员批准后，管理系统轮询得到充值码。
- [ ] 管理系统验签、兑换并调用 ack。
- [ ] 重复轮询不会产生第二个订单或第二次入账。
- [ ] 销售人员拒绝后，管理系统不会拿到充值码。
- [ ] 管理系统上报额度汇总后，销售总台客户页面能看到最新数据。
- [ ] 销售总台能调用 `/integration/sales/v1/ping` 并获得版本信息。
- [ ] 能分别执行龙信业务应用升级和 AgentScope 平台升级。
- [ ] 升级失败可以回滚，且失败结果能返回销售总台。
- [ ] 升级成功后，`app_version` 或 `core_version` 能返回目标版本。
- [ ] 内网断开、超时、服务重启等情况不会导致重复充值或错误升级。
