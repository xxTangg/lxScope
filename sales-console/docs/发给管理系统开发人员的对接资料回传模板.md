# 新销售总台与管理系统对接资料回传模板

> 用途：请将本文档完整交给管理系统开发人员，并要求他交给自己的 AI 按本文档逐项整理、填写后回传。
>
> 本文档不是让 AI 重新设计接口，而是让 AI 收集并整理管理系统现状、待实现接口、网络条件、升级方式和联调资料。
>
> 如有暂时无法确认的内容，请填写“待确认”，并说明由谁、在什么时候确认；不能留空，不能只写“按现有系统处理”。

---

## 一、请交给 AI 的处理要求

请将本模板作为唯一收集清单，完成以下工作：

1. 阅读本文档和销售总台提供的接口文档。
2. 向管理系统开发人员、运维人员和产品人员收集真实信息。
3. 严格按照本文档的章节顺序整理结果。
4. 保留接口路径、字段名、状态值和版本字段的原文，不要自行改名。
5. 已实现的内容填写“已实现”，未实现的内容填写“未实现”，不确定的内容填写“待确认”。
6. 对每个已实现接口提供真实的请求示例、成功响应示例和失败响应示例。
7. 对不能实现的接口说明原因，并给出预计完成时间或替代方案。
8. 最终输出一份可以直接用于销售总台联调的资料，不要只输出泛泛的技术总结。
9. 生产密码、生产 Token、私钥和敏感配置不要写入本文档或普通聊天消息，应说明安全交付方式。

销售总台与管理系统之间只通过 HTTP API 传递数据，不共享数据库，不直接读取对方数据库，也不依赖旧销售总台。

## 七、统一请求、响应和错误规范

请确认管理系统能够遵守以下规范：

### 7.1 请求头

```http
Authorization: Bearer <customer-api-token>
Content-Type: application/json
X-Request-ID: <请求链路 ID>
Idempotency-Key: <状态变更请求必填>
```

### 7.2 错误响应

```json
{
  "detail": {
    "code": "invalid_request",
    "message": "错误原因"
  },
  "request_id": "请求链路 ID"
}
```

### 7.3 状态码处理

| 状态码 | 含义 | 处理方式 |
| --- | --- | --- |
| 200/201 | 成功 | 处理响应 |
| 400 | 参数或业务状态错误 | 记录原因，不盲目重试 |
| 401 | Token 无效 | 告警并暂停调用 |
| 404 | 资源不存在 | 记录并人工处理 |
| 409 | 重复请求或状态冲突 | 按幂等结果处理，不重复入账或升级 |
| 429 | 请求过多 | 按退避策略重试 |
| 5xx/超时 | 服务或网络异常 | 指数退避，并使用相同幂等键重试 |

请回传管理系统实际支持的状态码和重试规则。
