# 新销售总台新手讲解手册

> 这份文档不要求读者懂代码。照着“怎么讲”部分，就可以向同事说明新销售总台是做什么的、数据从哪里来、各个页面怎么用。

## 一句话说明

新销售总台是销售人员使用的运营后台，用来统一管理已经交付给客户的龙信 AI 助手系统，包括客户资料、充值、Token 额度、消费情况、升级和操作记录。

它不是普通用户聊天的地方，也不是客户管理员的管理中心。它是销售人员管理多套客户系统的工作台。

## 30 秒讲解版

可以这样介绍：

> 这是新的龙信销售运营中心。每个客户系统在这里对应一条客户记录，销售人员可以查看客户的连接地址、上报状态、充值情况和剩余额度。客户管理员发起系统充值申请后，销售人员在这里审核并签发充值码；销售人员上传升级包后，也可以选择客户系统进行集中升级。新系统前端和后端独立部署，使用自己的数据，不依赖历史销售总台。

## 一、系统中有哪几类人

| 角色       | 在哪里操作             | 对销售总台的影响                                                 |
| ---------- | ---------------------- | ---------------------------------------------------------------- |
| 普通用户   | 客户系统的普通使用界面 | 提交的是个人或业务申请，不会直接进入销售总台                     |
| 客户管理员 | 客户系统的管理中心     | 审批普通用户申请；当系统额度不足时，向销售总台发起系统级充值申请 |
| 销售人员   | 新销售总台             | 管理客户、审核充值、签发充值码、查看报表和执行升级               |

### 最重要的权限关系

普通用户看不到管理中心；管理员可以看到管理中心。但销售总台不需要知道每一个普通用户是谁，它只接收客户系统级的申请和汇总数据。

也就是说：

1. 普通用户在客户系统中提交申请。
2. 客户管理员在客户系统中审批申请。
3. 如果客户系统的系统额度不足，管理员再发起系统级充值申请。
4. 新销售总台收到这笔系统级申请，销售人员审核处理。

## 二、数据是怎么流动的

```text
普通用户
   ↓ 提交普通申请
客户系统本地
   ↓ 客户管理员审批
系统额度不足？ ── 否 ──> 继续使用
   │
   是
   ↓
新销售总台收到系统级充值申请
   ↓
销售人员审核并签发充值码
   ↓
客户系统轮询、兑换并确认到账
   ↓
客户系统定时上报额度、消耗和版本
```

### 客户系统发给新销售总台的数据

- 系统级在线充值申请：金额、系统 ID、申请说明和时间。
- 使用量报告：剩余 Token、累计充值、累计消耗、累计赠送和应用版本。
- 充值码轮询结果和到账确认。
- 历史离线充值码的 nonce，用于避免重复入账。

### 新销售总台发给客户系统的内容

- 审核结果和签名充值码。
- 连接探测请求。
- 远程重置客户管理员密码的请求。
- 升级指令和升级包下载地址。

客户系统通过新系统定义的 API 接入；销售人员前端通过登录会话接入。两种身份不能混用。

## 三、左侧菜单分别做什么

### 1. 经营总览

打开后台后首先看到的页面，回答四个问题：

- 最近 30 天签发了多少充值额度？
- 当前有多少套客户系统？
- 有多少笔充值申请等待审核？
- 客户系统最近上报的额度总量是多少？

下面的趋势图、待办列表和系统运行概况用于快速判断今天需要处理什么。

### 2. 客户系统

这里一行代表一套已交付的客户系统。

客户清单包含：客户名称、备注、配置地址、最近来源 IP、最近上报、累计充值、档位和状态。

点击客户后，可以：

- 修改客户名称、系统 ID、协议、端口、IP、环境、联系方式和备注。
- 查看客户最近一次上报和来源 IP。
- 查看客户 API Token。
- 签发一次性离线充值码。
- 查看在线和离线充值订单。
- 查看消费与上报历史。
- 在客户地址可访问时远程重置客户管理员密码。

### 3. 充值审核

这里处理客户系统提交的在线充值申请。

- 批准：填写确认金额，系统生成签名充值码。
- 拒绝：填写拒绝原因，申请结束。
- 客户系统之后会自动轮询充值码，并在兑换成功后确认到账。

销售人员不应该把普通用户的个人申请直接当作销售订单；只有客户系统级充值申请才进入这里。

### 4. 对账中心

用来对比客户的充值金额、最近上报余额和累计消耗，帮助发现数据不一致。

客户上报的是系统快照，不等于一笔新的充值订单。真正的销售金额以订单和审核结果为准。

### 5. 余额预警

根据客户多次上报的累计消耗，估算哪些客户可能需要续费或补充额度。只有数据足够时才会进行估算，数据不足会显示暂无数据。

### 6. 升级管理

升级管理分为两个对象：龙信 AI 助手应用和 AgentScope 核心平台。

操作顺序：

1. 选择 `.tar.gz` 升级包。
2. 填写版本号。
3. 点击“上传校验”。
4. 选择需要升级的客户系统。
5. 点击“升级所选”。
6. 查看逐客户升级结果。

上传时会检查 manifest、包类型、版本号、必要文件、路径安全和 SHA-256。客户系统升级前会备份，失败时尝试回滚，销售总台还会通过版本探测确认结果。

没有配置 IP 或状态不是正常的客户，不会出现在集中升级目标中。此类客户需要在客户自己的升级页面处理。

### 7. 总部公钥

显示充值码验签所需的公钥。公钥可以分发给客户系统，私钥只保存在新销售总台，不能泄露。

### 8. 系统设置

包含三部分：

- Token 兑换汇率：只影响后续生成或批准的充值码。
- 修改登录密码：修改当前销售人员密码。
- 操作记录：查看谁在什么时间调用了什么管理接口。

## 四、前端和后端是什么关系

```text
浏览器
   ↓
admin-web 前端（页面和按钮）
   ↓ HTTP API
sales-api 后端（鉴权、业务规则、数据和升级）
   ↓
客户系统
```

- 前端负责显示页面、表单和操作按钮。
- 后端负责真正的权限判断、金额校验、签名、数据保存和客户系统调用。
- 前端和后端可以分别构建、分别部署。
- 新项目使用自己的数据目录和配置，不读取历史销售总台的代码或数据库。
- 客户系统只依赖新销售总台公开的 API，不依赖后台内部代码。

技术规范上，前端使用 React、TypeScript、Vite、pnpm、ESLint 和 Prettier；后端使用 TypeScript + Express 分层实现。

## 六、开发环境怎么启动

准备 Node.js 20.x 和 pnpm 9.15.9，然后执行：

```powershell
cd sales-console
corepack enable
pnpm install
pnpm dev:api
```

再打开一个终端：

```powershell
cd sales-console
pnpm dev
```

打开：

- Web：`http://127.0.0.1:44101`
- API：`http://127.0.0.1:44100`
- 健康检查：`http://127.0.0.1:44100/health`

开发环境默认账号是 `admin`，默认密码是 `change-me`。生产环境必须通过环境变量设置管理员密码，不能继续使用默认密码。

## 七、常见问题怎么判断

### 页面打不开

先访问健康检查地址。如果 API 没有返回 `ok: true`，说明后端没有启动；如果 API 正常但 Web 打不开，检查前端开发服务或 Nginx。

### 客户列表为空

这不代表功能缺失，通常表示还没有创建客户。先在“客户系统”页面创建一套客户记录。

### 升级页面没有客户

只有同时满足“状态正常”和“已配置 IP”的客户，才会出现在集中升级目标中。

### 客户管理员看不到管理中心

这是客户系统内的权限问题，不是销售总台页面问题。需要确认登录用户是否具有管理员权限。

### 销售总台收不到普通用户申请

这是正常设计。普通用户申请先留在客户系统；只有管理员审批后，因系统额度不足而提交系统级充值申请，销售总台才会收到。

## 八、给别人讲解时的重点

讲解时记住下面五句话即可：

1. 新销售总台管理的是“客户系统”，不是普通用户的个人申请。
2. 普通用户申请先经过客户系统，管理员审批后才可能间接影响销售总台。
3. 销售总台负责审核系统级充值、签发充值码和管理客户交付状态。
4. 客户系统定时把额度、消耗和版本上报给销售总台，销售总台据此做经营展示和预警。
5. 新销售总台是独立项目，自己的前端、后端、数据和 API 都不依赖历史销售总台。
