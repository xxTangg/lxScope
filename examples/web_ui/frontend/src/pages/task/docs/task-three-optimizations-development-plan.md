# Task 三项优化开发方案

## 目标与当前交付

围绕业务模板可理解、可直达，以及执行过程可检查三项目标优化 Task 页面：

1. 提供包含界面图示、模板理念、九个场景和知识沉淀边界的在线用户手册。
2. 为九个模板卡片增加问号帮助入口，一键打开对应的手册场景章节。
3. 在“执行情报”中增加可追溯的合规、安全与操作合规验证结果。

本次已完成前两项的前端交付：手册位于 `public/task-user-guide.html`，模板帮助入口位于 `task-template-gallery.tsx`。手册中的图 1、图 2 是基于当前页面结构和拟议检查区绘制的界面示意图，示例检查状态不代表真实运行结果。第三项需先增加服务端检查结果契约和执行时校验，再接入执行情报，避免页面显示没有证据支持的“通过”。

## 方案一：Task 在线用户手册

### 内容结构

- 模板设计理念：固定流程、明确输入/输出、能力依赖、失败处理和人工复核边界。
- 快速开始：打开业务模板、选择场景、补齐输入、检查运行条件、执行并复核结果。
- 九个业务场景：用途、准备资料、步骤、预期输出和能力边界。
- 知识沉淀说明：区别知识库检索、单次任务证据/图谱和长期知识库写入。
- 执行情报说明：轨迹、智能分析、工具、产物及目前已有的运行前能力检查。
- 合规、安全与操作检查方案：标注现状和计划边界，避免把设计示意误认为已上线能力。

### 发布和维护

- 手册作为 `public/task-user-guide.html` 随前端静态资源构建、部署，基础地址采用 Vite `BASE_URL`，兼容子路径部署。
- 各业务场景使用稳定锚点，例如 `#scenario-s07-report-generation`；目录可从手册任意章节返回。
- 模板变更时维护对应章节，版本以服务端模板卡片显示值为准。建议后续由模板 ID 与场景元数据统一生成导航，减少手工 ID 漂移。
- 手册支持响应式布局和打印/另存为 PDF；图示说明为界面示意，正式验收时建议在已部署环境截取真实页面替换。

## 方案二：九个模板的一键帮助入口

### 交互规则

- 在每张模板卡片右侧放置 28px 的 `CircleHelp` 图标按钮，鼠标悬停显示场景名称，键盘焦点可见，提供 `aria-label`。
- 问号按钮与模板选择按钮作为并列控件，避免把按钮嵌套在按钮内；点模板主体仍只切换预览，点问号则打开新标签页。
- 新标签 URL 使用 `BASE_URL + task-user-guide.html + #anchor`，保持 Task 页面和用户当前选择不变。
- 未识别的模板 ID 不生成错误链接；目录服务返回九个模板时逐个显示帮助入口。

## 方案三：执行情报的三类检查

### 页面位置

在 `TaskRunPanel` 的执行情报区域，放在顶部运行状态和标签页内容之间，显示本次 Run 的检查摘要。点击摘要展开详情，详情项可定位到对应节点、工具调用或证据。运行中随事件更新；终态 Run 可查看完整记录。已有的运行前能力检查继续留在 Task 主区，并通过 Run ID 与执行情报关联，不重复伪装成业务合规结论。

摘要显示每类检查的状态和数量；详情至少包括检查点、结果、说明、证据来源、规则/策略版本、检查时间、关联节点和用户下一步操作。不同状态用文字、图标和颜色共同表达，不能只靠颜色。

### 三类检查范围

| 检查 | 检查时机 | 核心内容 | 阻断规则 |
| --- | --- | --- | --- |
| 合规检查 | 运行前、读取/生成关键节点、最终结果 | 适用制度/规则版本；输入资料是否获准；必需字段；引用来源、完整性和明确的政策约束 | 规则来源、适用范围或必要证据缺失时标记“未检查/待复核”；定义为硬性条件的失败项阻断后续步骤 |
| 安全检查 | 数据读取、工具调用、结果外发边界 | 当前主体/租户和资源权限；知识库范围；敏感字段；凭据泄露；外部目标和数据最小化 | 权限被拒、主体越权或策略拒绝时阻断；无法确认权限时不将操作视为通过 |
| 操作合规验证 | 任何可能改变业务状态的动作之前及之后 | 动作类别；目标资源；授权人/审批记录；显式确认；幂等键；执行回执/失败状态 | 写入、发送、结算等动作没有审批/确认凭证时不得执行；执行后没有回执时显示“结果未确认”，不得记为成功 |

合规规则结论与法律意见、模型判断、权限检查要分开记录。模型可以帮助发现需要复核的内容，但不能单独将合规状态置为“通过”。

### 服务端数据契约建议

为每个检查结果定义稳定结构，存入 `TaskRunRecord` 并通过现有轮询/SSE 更新给前端。建议字段：

```text
id, category, check_key, status, severity
step_id, action_id, title, message
policy_id, policy_version, evidence_refs[]
checked_at, checker_type, actor_id
blocking, remediation, approval_ref, execution_receipt
```

状态建议：`passed`、`failed`、`review_required`、`not_checked`、`checking`、`blocked`。错误结果需返回稳定 `error_code`，UI 展示的消息不得携带访问令牌、凭据或完整敏感原文。证据链接须继续经过当前用户权限校验。

### 执行时序

1. Run 创建时做能力与权限预检，并把预检结果关联本次 Run。
2. 每个节点开始前按节点能力与动作类型做规则/安全检查；不通过或待确认时挂起或阻断该节点。
3. 外部副作用执行前检查审批/用户确认、目标、幂等键和权限；执行完成后持久化回执。
4. 最终输出节点校验来源证据、必需内容和约束；需要专家判断的部分标记待人工复核。
5. 结构化检查结果随 Run 事件持久化，在执行情报中实时呈现并支持重载后恢复。

### 前端实现建议

- 在 `task-run-panel.tsx` 增加 `RunChecksSummary` 与可折叠 `RunCheckCard`，接入 `TaskRunRecord` 新字段；避免把检查逻辑写在 UI 客户端。
- 通过 `category`/`status` 做固定文案映射，不直接信任服务端返回的原始 HTML。
- 失败或阻断项默认展开；通过项默认收起；未检查项明确提示原因和责任方。
- 如有审批/确认操作，调用独立 API 并持久化操作者、时间和目标；不能只在浏览器本地维护确认状态。
- 对敏感证据只展示最小摘要与可控跳转，不在执行日志中复制凭证或完整敏感内容。

## 迭代顺序

### P0：手册与模板入口（本次前端交付）

- 发布在线手册与九个稳定锚点。
- 增加九个模板问号入口和新标签页跳转。
- 检查键盘可访问性、子路径 URL 和未知模板 ID 的回退处理。

### P1：检查结果契约与只读检查

- 对齐后端检查模型、Run 持久化字段和 SSE/REST 序列化。
- 接入现有运行前能力/权限/数据源检查和报告引用校验，并显式标注各项检查边界。
- 建立规则版本、证据引用和失败码的审计字段。

### P2：副作用动作的审批护栏

- 为写入、对外通知、归档和 ERP 等 Tool 增加动作分类。
- 实现确认/审批、幂等与回执；缺少任一必要证据时阻断。
- 在执行情报中显示待确认、已批准、已执行、结果未确认和失败状态。

## 验收标准

- 9 个服务端模板均显示独立问号入口；每个链接打开正确锚点，直接从 URL 打开也能定位章节。
- 手册九章的场景名称、模板 ID、版本、输入和业务边界与模板定义一致；知识检索与永久入库表述准确。
- 子路径部署下问号链接仍指向当前站点的手册，不受 `/task/:taskId?` 路由影响。
- 执行情报中的状态来自服务端持久化检查结果；Run 刷新/重连后仍一致。
- 缺少策略、证据或权限时显示“未检查/待复核/阻断”，不得默认“通过”。
- 副作用请求缺少审批/确认或幂等条件时不会调用下游写入接口；成功结果保留可追溯回执。
- 真实截图替换手册中的界面示意后，截图需来自目标版本页面并遮蔽真实项目数据、用户信息和敏感字段。

## 风险与依赖

- 不同部署版本可能提供不同模板版本；手册需注明版本，后续可从模板 API 动态读取场景元数据。
- 规则库和审批源未接入时，合规/操作检查只能显示未检查，不能用静态 UI 或模型措辞填补。
- 对外写入可能造成业务副作用，必须沿用后端权限、审批和幂等校验，不能只增加前端按钮。
- 手册中已提供基于当前组件布局绘制的界面示意；替换为部署环境的真实截图应在实际数据脱敏后完成。
