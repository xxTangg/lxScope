## ① 侧边栏：纯图标栏 → 可折叠文字标签

**现状**：窄图标 + 悬浮 tooltip，无文字、无展开态。  
**问题**：功能入口发现成本高，新用户要逐个悬浮才知道是什么；管理员入口（管理后台、可观测性）埋在底部菜单，不显眼。

**做法**

- 项目已用 `SidebarProvider`（shadcn sidebar），把 `collapsible="icon"` 的折叠态做成可切换：默认图标态，点击顶部的展开按钮 → 图标 + 文字标签。
- 给两组菜单加**分组标题**（如「工作区」「资源管理」），让分区一眼可辨。
- 管理员专属入口（管理后台 / 可观测性）在展开态显式列出，并加一个「管理员」角标（`Badge`），提升辨识度。
- 保留折叠态为默认，不占内容区宽度。

**验收**：新用户不悬浮也能叫出每个入口的名字；管理员能直接看到后台入口。

## ② 新建会话：简化操作步骤

**现状**：要真正开始聊天，用户得先建 Agent → 再点「新会话」→ 再配模型 / 权限 / MCP，步骤偏多。  
**优化目标**：**一键开聊，高级配置后置**。

**做法**

- **智能默认值**：进入 `/chat` 时，若已有 Agent 则自动选中最近使用的那个；若该 Agent 下无会话，直接自动创建一个空会话并聚焦输入框 —— 用户进来就能打字，不用先点「新会话」。
- **模型继承**：已实现（新建时继承当前会话的 `chat_model_config` 与兜底模型），可再放宽为「继承该 Agent 下任意会话」并记忆，避免删掉最后一个会话后配置丢失。
- **高级配置后置到右栏**：模型、权限模式、MCP、技能、知识库都不该阻塞「开始聊」，一律放到右栏面板里随时改。首次进入给一个默认权限模式（建议 `accept_edits` 或 `default`），并提示「可在右侧调整」。
- **空态引导**：无 Agent / 无会话时，空态里放一个醒目主按钮「创建第一个智能体」，一键走完创建 + 建会话，落到输入框。
- **减少弹窗层数**：新建会话不再弹对话框收集信息，直接用默认值创建，名字自动取（如「新会话」），需要时再重命名。

**验收**：从打开页面到发出第一条消息的点击次数明显下降（目标：已有 Agent 时 0 次额外点击即可输入）。

## ③ 全站原生弹窗 → 项目自带 Dialog + sonner Toast

**现状**：`window.alert` / `window.confirm` 散落在 admin、task、套餐卡等处，跳出设计体系、不可主题化、不可翻译。  
**做法**

- **确认类** → 复用现成的 `@/components/dialog/DeleteDialog.tsx`（`open` / `onOpenChange` / `title` / `description` / `onConfirm`，自带 loading）。非删除语义（终止 Run、撤销会话）可复制一份 `ConfirmDialog.tsx` 或给 `DeleteDialog` 加 `variant`。
- **结果通知类** → `import { toast } from 'sonner'`（已挂 `App.tsx`），用 `toast.success / error / message`。
- **删调试弹窗**：`admin/index.tsx:183` 那个 `alert(JSON.stringify(...))` 直接删掉，改成页面卡片或一句 toast。
- **顺带**：把确认文案里写死的中文抽进 i18n（如 `task.*`），双语才能真正生效。

**验收**：全站再无 `window.alert/confirm`；切英文后所有弹窗文案跟随。

## ④ 全站功能：突出重点 + 记录使用率

**现状**：功能铺得满，高频和低频权重一样，新用户不知道先用什么；也没有数据支撑「哪些功能真的在用」。  
**做法**

*（A）记录使用率 —— 埋点*

- 在统一的请求层（`src/api/client.ts`）和路由切换处加**轻量埋点**：记录功能入口点击、页面停留、关键操作（建会话 / 跑任务 / 装 MCP / 传知识库…）。
- 用 `react-router` 的路由变化 + 事件委托，给高频按钮挂 `data-track="xxx"` 属性统一采集，避免每个组件手写。
- 数据先落本地（后端已有 `/admin/observability` 可观测性），后续接进去做漏斗和留存。

*（B）突出重点 —— 信息层级*

- **首页落地即聊天**：把聊天作为默认主入口，其余功能收进侧栏。
- **高频入口前置**：聊天、任务、管理后台放一组且带文字；知识库 / MCP / 技能归为「资源」，做次级分组。
- **低频高级功能折叠**：策略、审计、升级、销售中枢等管理员低频项，收进「高级」折叠区。
- **首屏只留一个主行动**：空态突出「开始对话」，不并列一堆按钮。
- **持续收集**：把埋点数据做成简单的使用率看板（接 `/admin/observability`），按「用得多 / 用得少」定期调整导航顺序。

**验收**：关键操作有埋点；导航按实际使用率排序，低频项有折叠。

## ⑤ 聊天页右侧资源面板：栅格平铺 → 图标栏 + 单面板

**现状**：右侧 `PanelDock`（`components/panel/PanelDock.tsx`）把 6 个资源面板（计划 / MCP / 当前技能 / 权限 / 知识库 / 团队）按「可拖拽栅格」平铺——每列最多 2 个、每列最窄 20rem，入口在输入框工具栏的勾选下拉。另有三处**自动弹出**：技能面板（从技能目录跳转）、团队面板（`team_updated` 事件）、计划面板（首批任务到达）。布局持久化在 `localStorage.chat_panel_layout`。

**问题**（对应截图）

- 一次开 6 个面板 → 3 列并排，聊天区被压到不足一半宽度；而多数面板是**空态大卡片**（暂无规则 / 暂无 MCP / 暂无任务），信息价值为零却占最大空间。
- 自动弹出会叠加：技能 + 团队 + 计划先后触发，用户一个都没主动开，界面也会被塞满。
- 勾选菜单只有开关，看不出哪个面板里有内容；关闭要逐个点 X。

**做法（推荐 A：右侧图标栏 rail + 单面板，参照 Cursor 布局）**

1. **PanelDock 改造为「图标栏 + 单面板」**：
   - 最右保留一条窄图标栏（约 2.5rem），纵向放 6 个面板图标。
   - 点图标 → 右侧展开**一个**面板（单列、宽度可拖，20–32rem）；再点同图标或 X 收起。任一时刻最多 1 个面板展开，聊天区宽度有保底。
   - 图标加**状态点**：面板有内容（有任务 / 有团队 / 有规则）亮小圆点，hover tooltip 给摘要（如「计划：3 项任务」）——不开面板也能感知。
2. **自动弹出改为「自动打开该面板」**：三处自动触发逻辑保留，但目标都是同一个单面板槽位——后触发的替换先触发的，不再追加成排。
3. **空态瘦身**：空面板收窄为「图标 + 一句话 + 行动按钮」，不再撑满整栏高度。
4. **持久化调整**：`chat_panel_layout` 改记「最后激活的面板 key」，刷新后恢复；原勾选下拉保留，与图标栏状态双向同步。

**备选 B（保守，工作量小）**：栅格不动，只做三条——①自动弹出上限 1 个，超出替换而非追加；②空面板自动折叠为一条标题条；③默认列宽 22rem → 18rem。治标，6 面板同开时依然挤。

**验收**：正常对话时右侧只剩图标栏，聊天区宽度 ≥ 75%；任一时刻最多 1 个资源面板展开；有内容的面板在图标栏有状态点；三处自动弹出行为仍可达，但不再面板堆积。

## ⑥ 日程页：做成「智能体执行节拍表」，不是第二个飞书日历

### 为什么不能照搬

飞书 / Google 日历解决的是「**人**在某时要去某地」——母题是格子、事件块、拖拽排期、参会人。
本页的本质是「某个**智能体**在某时**自动跑一次**」——用户真正关心的是：

> 它跑了吗？跑得怎么样？下次什么时候跑？几个任务会不会撞一起？

这四件事，人类日历一件也不回答。**照搬飞书＝把自己最值钱的信息丢掉**。
所以本项目的视觉母题不取「格子 + 事件块」，而取 **节奏（Cadence）+ 结果（Outcome）+ 负载（Load）**。

**可用数据**（已确认存在）：`GET /schedule/{id}/sessions` 返回每个定时任务的历史执行会话
（`SessionRecord[]`，含时间戳）——即「执行结果」这一维度**现在是拿得到的**，只是前端没用。这是差异化的底气。

### 差异对照

| 维度 | 飞书 / Google 日历 | 本方案（龙信日程） |
| --- | --- | --- |
| 主角 | 「今天」和「我的空闲」 | **「下一场」**（未来最近一次执行 + 倒计时） |
| 一格代表 | 一个事件块 | **当天执行的密度与成败**（底色深浅 = 次数，状态点 = 成功/失败） |
| 点格子 | 直接新建日程 | 先**看**这天跑了什么（Day Sheet），「加任务」是次要动作 |
| 侧栏 | 「即将到来」事件列表 | **节拍轴**：一任务一行，未来 30 天触发点排成点阵 |
| 空态 | 插画 + 引导文案 | **任务模板超市**（每日简报 / 每周汇总 / 每月对账），一键起任务 |

### 五个差异化模块

**A. Next Up 条（替代顶部大月份标题）**
顶部不再放大号「2026年11月」，改放一条：`下一场 · 11月3日 09:00 · 每日简报 · 还有 2 小时 14 分`，右侧带「立即执行」。
月份标题降为次级信息。理由：AI 任务日历的时间锚点是**未来**，不是「今天星期几」。

**B. 节拍轴 Cadence Rail（放在月历右侧，替代「即将到来」列表）**
每个定时任务一行（任务名 + cron 一句话），右侧画出未来 30 天它的触发点，形成**条形码式点阵**。
一屏即可看出「周一早上扎堆三个任务」「每月 1 号只有一条」——撞车与空档一眼可见。这是日历类产品**没有的视角**。

**C. 结果热力月历（改造现有月视图）**
格子不再只放事件 chip：
- 底色深浅 = 当天执行次数（0 次保持原底，越多越重）；
- 右下角状态点 = 当天执行结果（全绿 / 有红 / 部分进行中）；
- hover 出「3 次执行 · 2 成功 1 失败」。
数据源即 `scheduleApi.listSessions`。一眼看出「这个月哪几天挂了」，是纯人类日历给不了的价值。

**D. 点格子 = 看那天（Day Sheet）**
点击任意格子，在下方/侧边展开轻量面板：这天有哪些任务、各属哪个智能体、各自最近一次结果；
底部一个「在这天加任务」的小按钮。与飞书的默认动作**相反**——我们默认给「复盘」，新建退居其次。

**E. 空态 = 任务模板超市**
整月无任务时不放插画，放 3–4 个高频 cron 模板卡片（每日 09:00 简报 / 每周一汇总 / 每月 1 号对账 / 每天巡检），
点一下预填好频率与时间，只需选智能体。空白月直接变成起任务的入口。

### 视觉差异化

- 不用「白底圆角卡片 + 蓝色事件块」这套飞书/Google 的通用视觉；
- 采用**密度渐变 + 状态点**作为母题，配色跟随站内主题色，圆角/间距与聊天页、任务页统一；
- 时间数字用等宽字体（任务时间比会议时间更需要精确对齐），弱化「卡片阴影」，强化「数据感」。

### 分阶段

| 阶段 | 内容 | 依赖 |
| --- | --- | --- |
| P0 | A Next Up 条 + D 点格子 Day Sheet + 月份标题降级 | 纯前端 |
| P1 | B 节拍轴 + C 结果热力（接 `listSessions`） | 需按任务并发拉 sessions，注意限流与缓存 |
| P2 | E 模板超市 + 周一起始可配 + 列表视图按天分组 | 纯前端 |

**不做**：日/周视图、拖拽改期、多人订阅、节假日图层——要么超出「定时任务可视化」的定位，要么依赖后端新能力。

**验收**：顶部默认显示「下一场」而不是月份；月历格子能看出执行密度与成败；右侧节拍轴能看出任务扎堆；点格子能看到当天执行明细；空月给出可一键起的任务模板。

## ⑦ 管理员中心 + 可观测性分析：从「信息陈列」到「运营驾驶舱」

**范围**：`/admin`（总览/成员/配额/模型/技能/MCP/策略/审计/升级/推广，10 个子页）与 `/admin/observability`（总览/请求/Token/用户/模型/智能体/工具/技能/失败，9 个子页）。共用 `AdminLayout`，靠 `pathname.startsWith('/admin/observability')` 切换两组侧栏。

### 现状盘点与实测诊断（2026-11-02 实测后端数据）

**结构问题**

1. **两个模块互相孤立**：应用侧边栏是两个入口，进入后各有一条内部侧栏，但两模块之间没有互切链接，也没有「返回工作区」。管理员想从总览跳到运行分析只能改 URL 或退出去重进。
2. **死代码**：`pages/admin/index.tsx`（763 行，`AdminPage`，含一套完整成员管理 UI）**没有被任何路由引用**——纯负担，且之前弹窗改造还白改了它。
3. **死接口**：配额页「流水账本」调 `GET /admin/ledger`，后端实际是 `GET /admin/quota/ledger` → **永远 404 报错**（已实测）。

**管理员中心·总览页问题**（截图所见）

4. 四张指标卡（token 池 0 / 累计充值 0.00 / 账号 1 / 状态正常）+「系统快照」（system_id=local-system、core_version=unknown）——全是**静态部署信息**，看完没有任何「今天系统发生了什么」。单机私有化部署下「token 池/充值」基本恒为 0，占了一级视觉位。
5. 「运行准备度」卡与指标卡内容重复（token 池、健康状态出现两次）。

**可观测性问题**（实测 `/admin/observability/overview?days=14`）

6. **口径污染（最严重）**：`request_count=5089` 里绝大多数是 **HTTP 事件**（健康检查、404/422），真正的模型调用只有 6 次。于是页面赫然写着「业务请求 5089 · 平均响应 0.03s」——数字虚胖 800 倍、延迟假性极低，完全误导。
7. **同页数据自相矛盾**：顶部「Token 用量」卡显示 0，但趋势图当天 `input_tokens=73898`。`token_usage` 聚合块与 `daily` 行的口径不一致（daily 从原始事件聚合，token_usage 从另一来源取），同屏两个数互相打架。
8. **趋势图视觉失效**：14 天里 13 天是 0，全部请求集中在今天——柱状图看起来像「没有数据」；且日切按 UTC，「今天」的边界与中国时区用户相差 8 小时。
9. **组件表只显示 2 行**（`slice(0,2)`）：「模型/智能体/工具」三张卡号称点击看详情，但首页只露出 2 条记录，信息量趋近于零。
10. **三个子页高度重复**：请求分析 / Token 用量 / 用户用量三个 focus 页拉的是**同一个接口**（共用 react-query key），只是卡片换序；「技能分析」还挂了两个路由（observability/skills 与 analytics/skills）。
11. 失败中心全是 `http_404/http_422` 这类机器码 + `system` 类型，没有用户可读的归类；审计页 limit=50 无分页无筛选；`TrendChart` 手写柱图（有滚动/tooltip/点选，底子可用）但不支持按小时聚合。

### 方案

**A. 口径与数据修正（先做，否则一切优化都在假数据上盖楼）**

1. 「业务请求」只统计模型/智能体调用，HTTP 事件单独归为「平台流量」并在 tooltip 说明；平均延迟只对业务请求计算。
2. 统一 `token_usage` 与 `daily` 的聚合来源（后端 `observability_analytics_api.py`），保证总览卡、趋势图、明细三方一致。
3. 日切时区改为系统配置的本地时区（或至少 Asia/Shanghai），「今天」不再漂移。
4. 修 `ledger` 接口路径（`/admin/ledger` → `/admin/quota/ledger`）；删除 763 行死代码 `pages/admin/index.tsx`。

**B. 管理员中心总览页重做（运营驾驶舱）**

5. 指标卡换血：`今日业务请求 / 今日 Token 消耗 / 今日活跃用户 / 近 7 天成功率`（数据全部已有，复用 observability 接口，带环比箭头）；「系统快照」收缩为页脚一行小字（版本/系统 ID/更新时间）。
6. 总览加两张导航卡：「去可观测性分析 →」「最近失败 Top 3」（点击直达 trace），打通两模块。
7. `AdminLayout` 顶部加模块切换 Tabs（管理员中心 ⇄ 可观测性分析）+ 返回工作区链接。

**C. 可观测性体验升级**

8. 三个 focus 页合并为「用量分析」一页（内部 Tab：请求 / Token / 用户），路由保留重定向；省掉两个几乎相同的文件。
9. 组件表 2 行 → Top 5 + 「查看全部」链接进对应详情页；模型/工具行也可点击（现在只有智能体可点）。
10. TrendChart：时间范围含「今天」时自动按小时聚合；提供「只看有数据的日期」开关；X 轴标签每 N 天抽稀。
11. 失败中心可读化：`http_404 → 接口不存在`等映射表；按「错误类型 × 影响用户数」聚合展示；保留跳转 trace。
12. 审计页补分页与类型筛选（复用配额页流水表格的模式）。

**不做**：自定义报表/导出、实时 WebSocket 推送、多租户对比——当前单机部署用不上。

### 分期

- **P0**（1+4+6+7，全是小改）：口径修正、死链/死代码清理、总览页换血、导航互切。做完数字可信、入口打通。
- **P1**：8+9+10（合并 focus 页、组件表扩容、趋势图聚合）。
- **P2**：11+12（失败可读化、审计分页）。

**验收**：总览页第一眼是「今天业务跑了多少、花了多少 token、成功率多少」；趋势图与 Token 卡数字一致；点「业务请求 6」不再出现 5089 的虚胖数；配额页流水不再报错；两个管理模块一键互切。
