## 回传口径

本报告严格区分双方职责：

- 销售总台的员工登录、客户管理、充值审批、发布包管理等 `/api/v1/*` 接口属于销售总台一侧，不把它们冒充为本项目已实现内容。
- 本项目需要负责客户管理系统侧的 `/api/v1/integration/*` 调用，以及提供给销售总台调用的 `/integration/sales/v1/*` 接口。
- 普通用户套餐申请只在客户管理系统本地形成订单；只有系统级额度不足时，管理员才通过销售总台充值适配器发起系统充值申请。
- 本报告中的“代码已实现”表示在当前工作区发现对应代码；由于当前环境没有销售总台测试地址、测试 Token 和完整运行依赖，均没有真实线上联调证据。
- 当前工作区新增的套餐模块位于 `examples/agent_service/longxin_admin/plan_billing/`，属于产品扩展层，不属于 AgentScope 通用核心。

## 七、充值码验签和公钥：未完成 / 不符合销售合同

当前代码已实现以下基础校验：

```text

payload Base64 解码
HMAC-SHA256 签名比对
system_id 一致性校验
tokens 为正整数
amount 为最多两位小数的字符串
nonce 使用 Redis SET NX 防止重复兑换
```

但销售总台资料要求：

```text
私钥只保留在销售总台
客户侧保存销售总台公钥
客户侧通过 /api/v1/integration/public-key 获取或配置公钥
校验版本、签名、system_id、订单号、nonce、issued_at、expires_at
```

当前差距：

- 客户侧使用 `LONGXIN_RECHARGE_CODE_SECRET` 共享 HMAC 密钥，不是销售合同要求的公钥验签模型；
- 没有实现 `/api/v1/integration/public-key` 拉取；
- 没有校验 `version`、`issued_at`、`expires_at` 的完整字段；
- 没有独立的公钥轮换、指纹确认和安全存储流程；
- 没有真实充值码联调结果。

结论：充值码只能算开发测试能力，不能宣称生产验签完成。

升级服务位于 `longxin_admin/upgrade/`，核心流程为：

```text
接收 operation_id
```

## 九、错误码、重试和幂等：部分完成

### 9.1 已有能力

- `SalesHubClient` 统一传递 Bearer Token 和 `X-Request-ID`。
- 网络超时区分为 `hub_timeout`，不可达区分为 `hub_unreachable`。
- 充值申请可保存本地订单，并按幂等键返回已保存结果。
- 充值同步遇到异常可返回 `unknown`，不会把网络超时强行标为成功。
- 充值码 nonce 使用 Redis `SET NX` 防止重复入账。
- 新增本地套餐订单审批使用幂等键和本地状态机，审批会执行系统池扣减/退款及账本写入。

### 9.2 当前不符合项

| 要求 | 当前状态 |
| --- | --- |
| 所有状态变更缺少 `Idempotency-Key` 返回 400 | 销售充值/同步/用量部分路由尚未强制 |
| 同一作用域同一幂等键但请求体变化返回 409 | 当前实现未保存请求体摘要，未完成 |
| 所有响应包含 `request_id` | 成功响应大多有；错误响应未统一包含顶层 `request_id` |
| 自动指数退避 | 未实现；当前仅保留未知状态并允许手工重试 |
| 远程重置按 `operation_id` 幂等 | 未实现 |
| 升级按 `operation_id` 幂等 | 升级接口尚未实现 |
| 充值、套餐分配、账本的跨进程原子事务 | 当前主要依靠进程内 `asyncio.Lock`，生产级 Redis/数据库事务待补 |

```json
  "request_id": "req-001"
}
```
