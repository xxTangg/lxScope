## 一、当前新增内容总览

当前项目新增了两块主要能力：

1. 独立的新销售运营中心：目录为 `sales-console/`，不依赖旧销售总台的代码、数据库、进程和部署目录。
2. AgentScope 知识图谱能力：挂接在知识库的文档解析、切分、索引流程中，并在 Web UI 中展示。

本次检查还发现一项环境问题：销售系统构建机当前使用 Node 24，而项目要求 Node 20，导致构建检查没有正常完成。这属于开发环境/发布流程问题，不是已经确认的业务逻辑 Bug，但必须在发布前处理。

## 二、新销售运营中心

### 2.1 已新增功能

- 销售人员登录和 HttpOnly Cookie 会话。
- 客户系统档案：客户名称、系统 ID、IP、协议、端口、环境、联系人、备注和启用状态。
- 客户 API Token：创建时生成，支持轮换并一次性显示。
- 客户连接验证：通过客户 Token 调用客户系统的 `ping` 接口。
- 在线充值申请审核：批准、拒绝、确认金额和处理记录。
- 一次性离线充值码签发、查询和状态跟踪。
- 客户额度和消费上报：展示客户系统最近一次上报、余额、累计充值和消耗等信息。
- 升级管理：分别支持 AgentScope 平台整体升级包和龙信业务应用升级包。
- 总部公钥展示、发布包下载和客户侧升级调用。
- 远程重置客户管理员密码。
- 对账中心、余额预警、操作审计和系统设置。
- PostgreSQL Docker 部署；未配置数据库时保留本地 JSON 存储，便于开发联调。
- 新接口统一使用 `/api/v1`、`snake_case` 字段、UTC 时间和金额字符串，接口清单见 `sales-console/docs/API-CONTRACT.yaml`。

## 三、知识图谱新增内容

### 3.1 后端能力

- 新增图谱数据模型：实体、关系、属性、别名和来源引用。
- 使用结构化输出模型从文档分片中抽取实体和关系。
- 实体和边使用稳定 ID，便于跨文档合并。
- 每个节点和关系保留来源文档、分片、文件名和页码等信息，支持追溯原文。
- 文档索引成功后异步抽取图谱，不阻塞向量索引主流程。
- Redis 保存“每个文档的图谱贡献”和“知识库合并图谱”。
- 删除文档或知识库时同步清理对应图谱数据。
- 支持已有知识库重新构建图谱，不需要重新写入向量。
- 图谱状态包含 `disabled`、`empty`、`building`、`ready`、`error`。

### 3.2 API 和前端

- 查询图谱：`GET /knowledge_bases/{knowledge_base_id}/graph`
- 重建图谱：`POST /knowledge_bases/{knowledge_base_id}/graph/rebuild`
- 支持按节点名称、别名、类型搜索。
- 支持按文档 ID 过滤，并限制节点和边数量，避免大图一次性撑爆页面。
- 前端新增知识图谱面板：状态、节点数、边数、搜索、重建、节点选中和来源查看。
- 图谱使用 Neo4j NVL 进行可视化，不代表当前部署新增了 Neo4j 数据库；实际持久化仍在 Redis。

### 3.3 当前使用条件

- 配置图谱抽取模型和可用的模型 API Key 后，图谱功能才会启用。
- 文档必须先完成解析、分片和向量索引，图谱才有可抽取内容。
- 没有模型 Key 时，接口会显示 `disabled`，这不是前端故障。
- 当前抽取属于 LLM 自动抽取，明天需要用真实业务文档检查实体合并和关系准确性。

## 四、已知 Bug、现象和原因

### Bug 1：升级管理的文件选择区域发生扭曲

**现象**：升级管理页面中，文件选择框、文件名提示和底部按钮区域互相挤压，出现文字重叠、控件被截断、左右板块高度或宽度不一致的情况。

**原因**：当前页面直接使用浏览器原生文件选择控件，并把它放在多列卡片布局中。原生控件的显示宽度受浏览器和系统影响，和固定宽度的卡片、按钮同时存在时会发生压缩；文件名较长时还会进一步撑坏布局。

**影响**：用户可能看不清当前选择的文件，也可能误以为上传成功；应用包和平台核心包的操作区域不够可靠。

**明日处理**：

- 改成统一的自定义上传区域：隐藏原生 input，只保留“选择升级包”按钮和文件名展示。
- 文件名超长时截断并显示完整名称提示。
- 两个升级卡片使用相同的网格列宽、内边距、按钮高度和底部对齐方式。
- 明确显示“未选择文件、已选择、校验中、校验成功、校验失败、升级中、完成/失败”状态。
- 用窄屏和宽屏各验证一次，禁止依赖浏览器原生控件的默认外观。

### Bug 2：“显示客户 Token”实际会轮换 Token

**现象**：按钮文案是“显示客户 Token”，但代码调用的是 `api-token/rotate` 接口。每点击一次都会生成新 Token，并立即使旧 Token 失效。

**原因**：按钮名称表达的是“读取”，实际实现表达的是“轮换并一次性展示”，前端交互语义不一致。

**影响**：如果管理系统已经配置了旧 Token，销售人员再次点击按钮后没有同步新值，连接验证就会返回“Token 无效”。这正是最容易重复出现的联调问题。

**明日处理**：

- 将按钮改名为“轮换并显示 Token”，并在操作前增加确认提示。
- 成功后明确提示“旧 Token 已失效，请立即复制并同步到管理系统”。
- 在页面上显示最近轮换时间和同步提醒。
- 补充 Token 轮换后的连接验证用例。
- 不建议为了方便而在前端长期读取数据库中的明文 Token；生产环境仍应坚持一次性展示、脱敏和轮换机制。

### Bug 3：销售系统构建检查受 Node 版本和依赖网络影响

**现象**：执行销售系统构建时，当前环境是 Node `v24.19.0`，但 `sales-console/package.json` 要求 Node `>=20.0.0 <21`；同时 pnpm 尝试访问 npm registry 时出现 `EACCES`，因此构建没有完成。

**原因**：项目工具链要求 Node 20，当前机器使用 Node 24；依赖安装还依赖当前环境的 npm registry 访问权限或本地缓存。

**影响**：目前不能把“构建通过”作为发布结论，生产镜像、前端产物和 API 产物还需要在符合要求的环境重新验证。

**明日处理**：

- 切换到 Node 20.x，并使用项目声明的 pnpm 版本。
- 补齐并固定 `pnpm-lock.yaml`，使用 `pnpm install --frozen-lockfile`。
- 在可访问 npm registry 或已准备离线依赖缓存的环境执行前端构建、后端构建和 lint。
- 记录 Node、pnpm、构建时间和产物版本，作为发布凭据。

### 风险 4：知识图谱抽取结果需要业务准确性验收

**现象/风险**：图谱技术链路已经接通，但当前没有足够的真实业务文档验收“同一实体是否被正确合并、关系方向是否正确、别名是否正确、来源位置是否准确”。

**原因**：实体和关系由 LLM 自动抽取，模型输出质量会受文档格式、文本切分、提示词和模型版本影响。

**影响**：图谱页面可能能正常显示，但出现漏关系、错关系或同一实体多个节点的业务问题。

**明日处理**：

- 准备 3 份真实但脱敏的业务文档，人工列出应出现的实体和关系。
- 上传、索引、查看图谱并逐项对照。
- 记录漏抽、误抽、重复节点和错误来源引用。
- 决定是否需要调整实体规范、关系词表、提示词或模型参数。
- 对大文档检查抽取耗时、Redis 数据量和前端渲染性能。
