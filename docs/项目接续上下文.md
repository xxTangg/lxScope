## 1. 一句话介绍

这是一个以 AgentScope 2.0 智能体框架为基础的龙信助手项目仓库。仓库包含三层产品：

1. **AgentScope Core**：智能体开发框架和通用运行时。
2. **lxScope / 龙信助手管理系统**：在 AgentScope 服务上构建的多租户 AI 助手，包含聊天、任务、知识库、资源管理、额度与管理中心等应用功能。
3. **新销售运营中心**：独立的多客户销售管理系统，通过 API 与各客户的 lxScope 实例对接。

销售运营中心是独立应用，不与历史销售系统共用代码、数据库或进程。它负责多客户运营；lxScope 管理系统负责单个客户实例中的用户、资源、额度和 Agent 运行。

## 2. 产品边界与角色

### 2.1 三个系统分别做什么

| 系统 | 面向对象 | 主要职责 |
|---|---|---|
| AgentScope Core | 开发者、应用运行时 | Agent、Model、Toolkit、事件流、Middleware、Memory、Workspace/Sandbox、RAG、MCP 等通用能力 |
| lxScope / 龙信助手 | 客户组织中的普通成员和管理员 | 聊天与任务执行、知识库、模型与资源使用、成员/租户管理、套餐额度、升级和销售中心连接 |
| 新销售运营中心 | 龙信销售人员 | 多客户档案、充值审核与交付、用量汇总、对账预警、发布包和批量升级 |

### 2.2 主要角色

- **普通成员**：在所属组织中使用聊天、任务和管理员已发布的模型、Skill、MCP 等资源；提交的个人申请先进入该客户 lxScope 内部。
- **客户管理员**：管理组织成员、资源和模型配置，审批客户内部申请、维护系统 Token 池，并代表客户向销售运营中心申请系统级充值或接收升级命令。
- **销售员工**：在销售运营中心维护客户、处理系统级充值、签发离线充值码、查看汇总用量和发布升级包。

销售员工身份与客户管理员身份分离。销售运营中心不读取客户的聊天内容、文档正文、模型密钥或普通用户个人明细。

### 2.3 充值与升级边界

**额度链路：** 普通成员在客户系统内提交申请 → 客户管理员在本地审批并消耗客户系统 Token 池 → 系统额度需要补充时，管理员向销售运营中心提交客户级充值申请 → 销售审核并交付充值码 → 客户系统轮询、兑换、确认并上报汇总用量。

**升级链路：** 销售运营中心维护 app/core 发布包并向客户系统发送升级命令 → 客户系统下载、校验、备份、应用、重启、健康检查，失败时按配置回滚。app 表示龙信业务应用，core 表示 AgentScope 平台整体。

## 3. 功能总览

下面将框架能力与应用界面功能分开说明。README 中列出的 AgentScope 功能不一定都由 lxScope 的 Web UI 暴露，也不代表每项能力都完成了生产验收。

### 3.1 AgentScope Core：框架与运行时

- **Agent 与多智能体**：ReAct 循环、结构化输出、中断与恢复、顺序或并行工具调用、Leader/Worker 团队协作。
- **模型接入**：OpenAI、Anthropic、Gemini、DashScope、DeepSeek、Moonshot、Volcengine、xAI、Ollama 等模型适配；聊天、Embedding 及部分多模态能力。
- **工具系统**：Toolkit、内置 Shell/文件/搜索工具、MCP 工具、Python 工具及 Skill 调用。
- **上下文与中间件**：系统提示、RAG、记忆、上下文压缩、工具结果卸载、模型和权限钩子。
- **事件和流式输出**：统一事件系统向前端传递推理、工具调用、消息及多模态结果。
- **权限与人工确认**：资源和工具权限控制、用户确认及不同运行权限模式。
- **Workspace / Sandbox**：本地、Docker、Apple Container、Bubblewrap、E2B、OpenSandbox、Daytona、Kubernetes 等执行后端。
- **服务能力与扩展**：会话/状态持久化、RAG、多渠道、MCP/Skill Hub、定时任务、Pipeline、A2A 和实时语音等。

### 3.2 lxScope / 龙信助手：用户侧与管理侧功能

- **登录与组织身份**：Logto SPA 登录、Organization 选择、组织角色与 API Scope 校验；当前也保留本地账号模式用于本地验证。租户身份会影响数据访问边界。
- **聊天与会话**：在 Web UI 中与 Agent 对话，使用模型、工具、Skill、MCP 和已授权的知识资源；不同会话保存各自的执行上下文。
- **任务计划与执行**：把较复杂目标生成可追踪任务，按 AgentStep、ToolStep、CodeStep 等节点运行并展示进度、产物和结果。MCP 工具不可用时不能假定 Task 会产生可执行 ToolStep。
- **模型与凭证管理**：由管理员管理模型配置和凭证，再按产品权限供 Agent 使用；密钥应只在后端环境或安全凭证存储中。
- **Skill 管理**：使用内置 Skill、用户 Skill 库和 Hub 资源；支持安装/同步、工作区暴露、调用和 Skill 使用观测。安装或可见不等于模型实际调用成功。
- **MCP 管理**：管理 MCP Server、工具、发布可见范围和授权；MCP 的进程、transport、session、工具列表和具体工具执行需要分别验证。
- **工作区与代码执行**：为会话提供工作目录和受控执行环境，可挂载或隔离工作区资源。
- **知识库与 RAG**：上传文档、解析与切分、向量索引和检索；后端可使用 Redis/向量数据库及文件存储。
- **知识图谱**：在知识库页面按需启用和生成实体/关系图谱，支持搜索、来源查看和交互式画布。当前实现是应用层异步功能，不属于 AgentScope 核心索引主链路。
- **组织管理与额度**：成员管理、管理员权限、套餐/订单、系统级 Token 池、额度账本、审计和组织内管理功能。
- **升级与销售集成**：客户实例连接销售运营中心，完成充值申请、用量上报、连接检查、升级包下载和远程升级。
- **运行分析**：管理员查看请求、Agent、模型、Tool/MCP、错误与用量分析；应用内事件缓存有容量上限，不能代替生产级持久化日志/Trace。

### 3.3 新销售运营中心

代码位于 sales-console/，有自己的前端、API、数据库与数据卷。

- 销售人员登录和注销，使用 HttpOnly Cookie 会话。
- 经营总览、充值趋势、待办和运行概况。
- 客户档案：system_id、连接地址、环境、联系人、状态和最近上报信息。
- 客户 API Token 创建/轮换；明文只在创建或轮换时一次性返回，轮换后旧 Token 失效。
- 在线系统充值申请审核、批准/拒绝、充值码交付和状态确认。
- 离线充值码签发和校验，使用 Ed25519 签名。
- 汇总额度与消耗上报、充值历史、对账和余额预警。
- 发布包上传、manifest 和 SHA-256 校验、客户选择、升级执行、重启后版本确认。
- 总部公钥、汇率设置、远程重置客户管理员密码和操作审计。

**实现限制：** 功能清单中仍记录升级任务尚未持久化为可重试任务、销售员工细粒度角色权限待补、Token 轮换缺少过渡期等生产化差距。是否已变化要以当前代码和最新验收为准。

## 4. 系统架构与主要调用路径

### 4.1 代码职责

- React 浏览器前端负责 UI、输入校验、API 调用和流式展示。
- lxScope FastAPI 应用负责认证、租户上下文、应用级 API、业务规则、数据访问和 AgentScope 运行入口。
- AgentScope Core 提供 Agent、Model、Toolkit、Storage、MCP、Workspace、RAG 等通用执行能力。
- 销售运营中心使用独立的 React/Vite 前端和 TypeScript/Express API。
- 两系统以客户专属 Bearer Token 和稳定的 system_id 进行集成；system_id 与销售中心内部 customer_id 不能混用。

### 4.2 信任边界

| 请求方 → 服务 | 用途 | 认证方式 |
|---|---|---|
| 客户普通用户/管理员浏览器 → lxScope API | 聊天、Task、管理功能 | lxScope JWT 或 Logto 组织 API Access Token |
| 客户 lxScope API → 销售 API | 充值申请、轮询/确认、用量上报、下载和连接校验 | 客户专属 Bearer Token |
| 销售 API → 客户 lxScope API | ping、远程管理/密码重置、app/core 升级命令 | 同一客户专属 Bearer Token |
| 销售人员浏览器 → 销售 API | 客户、订单、发布包和设置管理 | 销售人员 HttpOnly Cookie |

前端隐藏按钮不是权限边界；后端仍需逐个校验身份、组织、角色和客户 Token。

## 6. 数据与持久化边界

| 数据类型 | 当前主要位置 | 说明 |
|---|---|---|
| AgentScope Core 状态与存储 | RedisStorage/Redis | Core 仍使用 Redis 存储路径，不能因 lxScope 配 PostgreSQL 就认为所有状态都已迁移。 |
| lxScope Task 数据 | Redis 或 PostgreSQL | Compose 默认 LXSCOPE_TASK_STORE_BACKEND=redis；明确切换为 postgres 后使用 PostgresTaskStore。 |
| lxScope 应用业务数据 | 逐步接入 PostgreSQL 与 Redis | PostgreSQL 迁移基础已建立；认证、额度等不同模块的迁移状态并不相同，按当前实现逐项核对。 |
| 向量 | Qdrant 或配置的向量库 | RAG 向量，不是关系数据库。 |
| 文档、Blob、Workspace 数据 | 文件系统/命名卷或可选对象存储 | 数据卷需纳入备份计划，不能只备份 PostgreSQL。 |
| 知识图谱 | Redis 的 lxscope:kb_graph:* 命名空间 | 使用独立应用层前缀；不复用历史 AgentScope 原生图谱键，也不代表部署 Neo4j。 |
| 销售运营数据 | PostgreSQL；未配置时可回退 JSON 文件 | PostgreSQL 中当前有兼容 JSONB 存储层；发布包与 Ed25519 密钥在独立 sales_data 数据卷。 |
| Logto 身份 | Logto 自己的数据库 | 迁移 Logto 用户/组织 ID 不会自动更新 lxScope 业务数据外键或关联值。 |

租户安全原则：请求体传入的 tenant_id 不可信；后端应从已验证的认证上下文获取租户身份，并在 Repository 查询中强制包含租户范围。全局用户和租户 membership 是不同概念；AgentScope 兼容层可能使用 membership ID 作为隔离用户 ID。

## 7. 认证、配置和部署

### 7.1 Logto 登录需要保持一致的值

- API Resource 与前后端配置必须一致。
- 普通组织成员至少需要 agent:use；组织管理员还需要 tenant:manage。
- SPA Redirect URI 必须与浏览器实际访问地址逐项一致，包括协议、主机、端口和 /auth/callback。
- VITE_LOGTO_* 是前端构建参数；变更后通常需要重新构建前端静态产物。
- 浏览器访问地址和 Docker 后端访问 JWKS/Management API 的内部地址是两回事；localhost 与 Docker 服务名有不同网络语义。
- M2M Secret 仅限后端，不得放到 VITE_*、代码仓库或会话文本中。

### 7.2 主应用 Docker 服务

整理时 docker-compose.yml 中包含：

- Postgres 16：lxScope 应用业务数据库。
- Redis 7：AgentScope/Core 与应用缓存、会话及部分业务路径。
- Logto Postgres 17 与 Logto：自托管身份服务，默认主机端口为 3001（核心服务）、3002（管理控制台）。
- agentscope：FastAPI 后端，容器内 8000，默认主机 API 端口 8001。
- web-ui：前端默认主机端口 8000。

主应用默认本机访问 Web 为 http://localhost:8000，API 为 http://localhost:8001。端口可由根目录 .env 覆盖。实际操作前必须确认当前浏览器 URL、Compose project、端口映射和加载的 env 文件；项目历史中同时出现过 8000 与 18200 两个前端实例。

### 7.3 销售中心 Docker 服务

销售中心单独使用 sales-console/compose.yaml，默认 API 为 44100、Web 为 44101，另有自己的 Postgres 和持久化 sales_data 卷。不同 Compose project 默认可能处于不同 Docker 网络；容器服务名不能跨网络解析。真实集成前先确认网络、映射端口、system_id 和 Token。

### 7.4 开发热重载

主项目开发模式使用主配置和 docker-compose.dev.yml 叠加，源码挂载到后端并用 Vite HMR 提供前端热更新。开发覆盖文件不能单独运行。只有依赖配置变化时才需要 build；VITE_* 构建参数变化仍需重新构建前端。

销售中心的本地运行说明和 Docker 运行说明在 sales-console/README.md。当前工作树新出现的 sales-console/compose.dev.yaml 属未提交文件，不应当作已发布部署基线。

## 8. 关键应用功能的当前约束

- **知识图谱**：2026-09-22 记录了 PUT 缺失、同步生成阻塞、首屏空白等修复；生成现为后台任务。是否正确抽取实体、关系和来源，仍需真实脱敏资料人工验收。
- **MCP**：页面切换、Uvicorn reload 和跨请求复用曾触发 ClosedResourceError/cancel scope 异常。管理/Task 路径增加健康探测和重连思路，但 stateful stdio 全生命周期仍需回归；HTTP 200 不等于工具可调用。
- **Task**：无 MCP 工具时可能没有 ToolStep；需要校验节点类型、tool_name、参数 schema 和 Planner 输出。Task generation 有超时配置，需与当前运行值匹配。
- **可观测性**：请求可以用 X-Request-ID/X-Trace-ID 关联。应用内观测事件默认最多 50,000 条，进程重启会清空；要做生产保留需接入受管日志、指标或 OTLP 后端。
- **销售连接**：HTTP 200 可能仅表示验证接口正常返回；要看响应体中的业务状态和错误。客户 Token 轮换后旧 Token 立即失效，必须同步两边配置。
- **销售升级**：发布包要校验 manifest、路径穿越、文件必要项与 SHA-256。销售中心功能清单仍列有升级任务持久化/重试及细粒度角色等生产化缺口。
- **数据库迁移**：PostgreSQL 基础与 TaskStore 选项存在，不代表认证、额度、所有 Admin 状态都已从 Redis 迁完；迁移需分批导入、对账、回滚演练。

详细问题复盘见 [项目踩坑总结](./项目踩坑总结-2026-09.md)。

## 11. 新会话接手时的工作约定

1. 先读本文件和项目踩坑总结，再按任务范围读对应源文档；不要把 AgentScope Core、lxScope 应用和销售运营中心混为一层。
2. 检查当前分支、工作区差异、Compose project、服务端口和目标环境，再决定要改代码还是部署配置。
3. 应用层业务尽量放在 examples/agent_service；只有明确需要通用框架能力时才修改 src/agentscope。
4. 权限必须由后端执行；租户过滤从认证上下文取得，不能相信客户端 tenant_id。
5. Logto 回调、SPA App ID、API Resource、组织 Scope 和前端构建变量必须按实际运行实例核对。
6. 对外部系统问题区分代码逻辑、容器网络、外部凭据、授权、TLS/DNS 和页面错误隐藏；不要用 HTTP 200 单独宣布联通。
7. 修复记录中明确“未验收”的问题，完成运行或联调证据后再改成已解决。
8. 不将凭据、客户 Token、用户密码、密钥或私人数据写进这份上下文或公开上传的文件。
