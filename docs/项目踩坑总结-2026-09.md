## 二、Logto 登录与租户身份

### 1. 二次登录看到组织，但拿不到组织 API Token

**什么情况下：** 首次登录正常，退出后再登录；或进入组织选择页时，组织列表可见，但选择组织后不能进入 lxScope。

**出了什么问题：** Logto 登录回调和组织列表读取已经成功，失败发生在获取带组织上下文的 API Access Token 时，尚未到 lxScope 后端的 /auth/me。因此空 Token 不能直接证明是 agent:use 权限缺失。

**查到的根因：** 一次授权码交换日志显示成功，但没有 offline_access，tokenTypes 中没有 Refresh Token；同时审计日志里的 application ID 与项目 .env 中的 SPA ID 不一致，回调地址使用了 127.0.0.1:18200，而被检查的配置默认值是 8000。这说明当时浏览器很可能连到了另一套、旧的或使用不同构建配置的前端。

**具体解决办法：**

1. 在浏览器当前页面对应的 Logto 授权码交换日志中核对 application ID、回调地址、授权 scope 和是否返回 Refresh Token。
2. 核对实际运行前端的 VITE_LOGTO_APP_ID、VITE_LOGTO_ENDPOINT、VITE_LOGTO_API_RESOURCE，不要只看源码目录或另一份 .env。
3. 在 Logto SPA 应用中启用 offline_access，并登记实际浏览器使用的完整回调 URI，包括协议、主机、端口和 /auth/callback。
4. 若 VITE_LOGTO_* 改过，重新构建并启动前端镜像。它们通常在前端构建时写进静态产物，单独重启容器不一定会更新。
5. 只有已经拿到 API Token、后端随后返回 403 时，才继续查组织角色是否授予了 agent:use。

**避免误判：** “没有 Refresh Token 记录”是现象，不是根因；要继续核对是哪一个 SPA 应用实际完成了授权交换。

### 2. 账号被管理员禁用后没有退出

**什么情况下：** 管理员在 lxScope 中禁用组织成员，该成员仍停留在当前聊天页，页面不断出现红色错误提示。

**出了什么问题：** 禁用的是 lxScope 的成员状态，Logto 自身的浏览器登录会话仍然有效。后端返回专用的 403，但旧前端只把 401 当成必须退出的未授权状态，所以它继续留在聊天页。只清掉本地状态还会触发登录页自动跳回 Logto，形成重新登录或重复检查。

**解决办法：** 后端用可识别的禁用错误返回 403；前端识别该错误后清理 lxScope Token、退出 Logto，并停留在登录页提示联系管理员。登录页不自动重新发起登录，用户手动重新登录时才继续认证流程。

**状态：** 代码修复记录已完成；最终仍应在实际登录环境验证被禁用账号会退出、未被禁用账号不受影响。

### 3. 用户名或租户名显示为 ID

**什么情况下：** 页面左下角有用户名，但成员管理或租户相关页面显示 Logto 用户 ID / Organization ID。

**出了什么问题：** Token 中的 sub、organization_id 是稳定标识，不是适合展示的姓名和租户名称；不同页面也可能采用不同的数据来源。

**解决办法：**

- 租户名优先读取 Logto 返回的组织展示数据；暂时读不到时才回退显示 ID。
- 用户显示名如需从 Logto Management API 查询，使用服务端 M2M 凭据补充资料；M2M 应用必须具有所需的 Management API 权限。
- 检查服务端 M2M Token 请求的 resource 和 scope。项目修复记录中曾补上 scope: all。
- M2M Secret 只放服务端环境变量，不放 VITE_* 前端变量，也不贴到会话中。

**避免误判：** 只凭“已分配管理 API 角色”的截图不能证明当前运行容器取到了正确的 M2M Token，也不能证明资料查询成功。继续看后端日志和接口返回；页面显示 ID 可能是资料补充失败后的回退值。

### 4. 浏览器地址、回调地址和容器内部地址混用

**什么情况下：** 本机能登录，局域网用户不能登录；浏览器打开 http://logto:3001 出错；后端验证 Logto Token 或读取 JWKS 返回 404/连接失败。

**出了什么问题：**

- localhost 对浏览器指向用户自己的电脑，对 Docker 容器则指向容器自身。
- logto 这类 Compose 服务名通常只能由同一 Docker 网络里的容器解析，浏览器不能直接用它。
- Logto issuer 必须和 Token 中的 issuer 一致；给后端访问 JWKS 配置的内部地址不应随意替换公开 issuer。
- 回调 URI 必须逐字匹配；/callback 与 /auth/callback、localhost 与 127.0.0.1、不同端口都不是同一个地址。

**具体解决办法：** 浏览器使用可访问的 Logto 地址；后端 JWKS/Management API 使用后端容器可达的地址，例如同一 Compose 网络中的服务名或 Docker Desktop 的 host.docker.internal。先确认服务是否在同一个网络，再设置内部地址。改完后确认 Token issuer 仍与 LOGTO_ENDPOINT 匹配。

### 5. 使用了另一份旧 Logto 说明

**什么情况下：** 按相邻目录或旧文档配置 Logto，但当前代码登录失败。

**出了什么问题：** 项目曾经有文档默认使用 localhost:3001、回调路径 /callback、旧启用变量；而当前工作区使用的 Endpoint、SPA ID、路径可能已变化，部署还可能已切到 Logto Cloud。

**解决办法：** 以当前工作区的 docs/LOGTO_部署与权限配置说明.md、实际 .env、前端路由和容器配置为准，不要把同级旧仓库中的说明原样照搬。迁移脚本只搬 Logto 组织/成员/身份配置，不会搬 lxScope 业务数据库或 Redis，也不能迁移用户密码；跨租户后 ID 变化，业务数据映射需要单独处理。

## 三、Docker 部署、热重载与环境变量

### 1. 重启了另一个端口的前端

**什么情况下：** 用户浏览器打开 18200，但操作后页面完全没变；机器上另有一套 8000 的 Web UI。

**出了什么问题：** 同一仓库路径附近运行了不止一套 Compose 项目/前端实例。只按服务名重启 web-ui，可能重启了另一套端口映射；两边页面都可能正常返回 HTTP 200。

**具体解决办法：**

1. 先看浏览器当前主机和端口，再核对容器名、Compose project、端口映射、工作目录和 env 文件。
2. 对照这些信息后再重启；不要只根据服务名判断目标实例。
3. 重启后用用户实际访问的 URL 检查页面与后端状态。
4. 如果当前工具环境没有 Docker 命令或无法访问 Docker Desktop，就明确说明无法代为重启，不要把用户贴出来执行成功的命令说成自己执行的。

历史会话中，先重启了 8000 的前端，后来才发现用户实际访问的是 18200；这是典型的“操作成功但操作了错误实例”。

### 2. 开发 Compose 覆盖文件单独运行

**什么情况下：** 使用 docker-compose.dev.yml 启动时报缺少服务或配置错误。

**出了什么问题：** 开发 Compose 是覆盖配置，不是独立配置；只传覆盖文件会缺少主 Compose 中的服务定义。

**解决办法：** 运行开发环境时同时传主配置和开发覆盖配置，并使用目标环境正在使用的 Compose project 名称与 env 文件。项目脚本也区分普通模式与 -Dev：普通模式不启用热重载，-Dev 才加载源码挂载、后端 reload 和前端 HMR。切换模式前先确认要操作哪一个实例。

### 3. 修改 .env 后页面还是旧配置

**什么情况下：** .env 中的 Logto App ID、Endpoint 或 API Resource 已改，浏览器仍加载旧值。

**出了什么问题：** VITE_LOGTO_* 一般在前端构建阶段写入 bundle；重启现有容器不会重新生成 bundle。反过来，后端普通环境变量则通常需要重新创建容器，单纯刷新页面不会注入新环境。

**解决办法：**

- 前端 VITE_* 变化：用包含新变量的 .env 重新构建对应前端镜像。
- 后端容器环境变量变化：使用正确的 Compose 文件和 env 文件重新创建对应后端容器。
- 先确认命令实际读取的是哪一份 .env。历史会话中有命令读取上一级目录的 .env，而不是当前工作区根目录里的文件。
- 区分 restart、--force-recreate 和 --build 的效果；只改容器环境变量不一定需要重建镜像，只改前端构建参数通常需要重建。

### 4. Compose 的 orphan container 警告

**什么情况下：** 当前 Compose 文件没有定义已有的 Logto 容器，启动时提示 orphan containers。

**出了什么问题：** 容器可能由另一份 Compose 文件或项目创建。警告说明当前 Compose 配置看不到它们，并不等于启动失败。

**解决办法：** 先确认这些容器属于哪个部署；不要为了消除警告就加 --remove-orphans，否则可能删除仍在使用的 Logto 服务。确认网络和服务归属后再调整 Compose 配置。

## 四、知识图谱

2026-09-22 的修复日志记录了以下真实故障：

### 1. 点击“启用知识图谱”没有反应

**原因：** 前端 API 客户端没有 PUT 方法；异常只写到弹窗内部，没有显示给用户。  
**解决：** 补齐 PUT，读取并更新启用状态，并在弹窗外显示请求错误。

### 2. 预览按钮灰掉，无法查看为什么不可用

**原因：** 未启用状态直接禁用了预览入口，用户无法进入查看明确状态。  
**解决：** 预览入口始终可用，状态通过轻量设置接口读取。

### 3. 生成请求卡住页面约 100–112 秒

**原因：** API 同步等待 LLM 处理所有文档分片。  
**解决：** 改为后台任务，API 立即返回 building，前端轮询状态，失败原因保存在状态中并显示。

### 4. 有节点/关系但首屏画布近似空白

**原因：** 按存储顺序先截取节点，再筛选边，容易留下互不相连的节点；旧弹窗太窄，也挤压了画布。  
**解决：** 优先取带关系的连通子图，首屏限制节点和边数量，使用力导向布局并适配画布尺寸。

### 5. 图谱存储边界误解

图谱可视化使用 NVL 不代表系统部署了 Neo4j。修复后的图谱数据使用独立 Redis 前缀，生成路由在 lxScope 应用层；文档上传和向量索引不再自动触发图谱抽取。没有抽取模型 Key、文档未完成索引时显示 disabled 或空状态可能是预期结果，不一定是前端故障。

**状态：** 2026-09-22 记录了类型检查、语法编译和开发容器热重载验证；图谱抽取的业务准确性仍要用脱敏真实文档人工核验实体、关系、别名与来源。

## 五、MCP 与 Task

### 1. 安装后正常，切换页面再回来报 ClosedResourceError

**什么情况下：** stateful stdio MCP（如 browser-use）首次连接正常；页面切换、后端 reload 或重启后工具显示不可连接、tools=[]。

**出了什么问题：** 状态缓存中的 MCP client 仍标记为 connected，但底层 AnyIO stream/session 已关闭。后续请求继续使用旧对象就会触发 ClosedResourceError。日志还出现关闭动作在不同 task/cancel scope 中执行的 RuntimeError。

**解决办法：**

- Task 请求开始时实际探测 list_tools()，不能只看缓存里的 connected 布尔值。
- 探测失败时关闭旧 client、重新连接，再获取工具列表；仍失败就返回清楚的 MCP 错误。
- 管理端健康探测用短生命周期 client，避免污染 Task 复用的连接。
- 将创建、持有、使用、关闭和重连归到明确的生命周期边界；不能在一个 task 中创建资源、又在另一个 task 中退出其 cancel scope。

**状态：** 管理层的连接探测/重连和 Task 规划校验有改进记录；但 docs/mcp-lifecycle/mcp-lifecycle-bug-summary.md 明确记录 stateful MCP 跨页面、reload 和重连的稳定性尚未完成验收，不能把它说成彻底解决。

### 2. HTTP 200，但 MCP 仍然不可用

**什么情况下：** /mcp、/workspace/mcp、/resources/published 返回 200，页面仍显示 MCP 错误。

**出了什么问题：** HTTP 路由可响应，只说明 API 请求到达；不说明 stdio 子进程、transport、MCP session 仍活着，也不说明工具可调用。

**解决办法：** 分开检查容器 liveness/readiness、MCP session、list_tools()、工具权限和实际工具执行结果。容器 healthy、接口 200、MCP connected、MCP healthy、tool callable 是不同层次，不能互相替代。

### 3. 管理中心“分配 MCP”失败

**什么情况下：** 分配给所有用户或指定用户时提示 Cannot reach the server，刷新后用户侧仍不可见。

**当前结论：** 历史记录确认查询接口曾返回 200，但没有确认分配写入接口及数据库状态。因此权限、发布状态、缓存和写入接口异常都还不能作为确定根因。

**解决办法：** 先核对分配请求是否成功写入，再核对发布范围、目标用户可见性和用户侧查询结果；HTTP 200 只能作为链路证据的一部分。不要仅靠强制刷新掩盖后端发布状态不一致。

### 4. Task 没有生成 ToolStep

**什么情况下：** Planner 只产出 AgentStep/PythonStep，没有真正的工具节点。

**出了什么问题：** MCP 不健康或工具列表为空时，Planner 没有可选工具；另外旧计划也可能有空 tool_name、参数不符合 schema，或最终 Agent 只看到上一节点输出。

**解决办法：** MCP 工具可用性先于规划；使用真实工具清单和 schema，保存计划前校验工具名、参数和节点顺序，必要时让模型修复一次；最终 Agent 接收所有前序节点的结果。无工具时明确告知用户，不要静默退化成“看起来执行了工具”的纯文本回答。

### 5. 把不同类型错误都显示成 MCP 断连

**常见混淆：** ClosedResourceError 是生命周期错误；Permission required 是授权错误；TLS socket disconnect 是容器网络/代理/DNS/外部 API 错误。

**解决办法：** 先看异常类型和请求阶段，再决定重连、调整 PermissionContext，还是检查网络出口。不要所有异常都统一显示“无法连接 MCP”。

## 六、销售总台与管理系统对接

### 1. Docker 容器名无法跨网络解析

**什么情况下：** 管理端配置 http://sales-api:44100，或销售端配置 http://agentscope:8000，但连接验证失败。

**出了什么问题：** 两套 Compose project 建立了不同 Docker 网络；容器服务名只在本网络内解析。同一机器上的健康检查都成功，也不代表容器彼此可达。

**解决办法：** 先查看两侧容器实际加入的网络，再选择共享 Docker 网络，或使用宿主机网关和已发布端口。历史排查曾得到候选地址 host.docker.internal:44100 与 host.docker.internal:18201，但当时管理页面未成功保存全部设置，不能把它们当作当前已验证配置；端口必须按当前 Docker 端口映射确认。

### 2. 验证 API 返回 200，但连接仍失败

**出了什么问题：** 验证接口可以用 HTTP 200 返回业务结果，真正的失败原因在响应体里；旧页面只显示上行/下行状态徽标，没有展示 error.code 和 error.message。

**解决办法：** 查看验证响应中的业务状态和错误码。上行 failed / 下行 unknown、outbound/inbound 等字段描述的是连接方向，不能单看 HTTP status。页面应展示后端返回的具体错误，方便区分网络不可达与 Token 被拒。

### 3. “显示客户 Token”会让现有连接失效

**什么情况下：** 销售人员再次点击显示 Token，管理系统随后报告 Token 无效。

**出了什么问题：** 按钮实际调用 api-token/rotate，每次都会生成新 Token 并立刻废弃旧 Token；按钮文字却让人以为只是读取原值。

**解决办法：** 将动作明确为“轮换并显示”，操作前确认，成功后提醒旧 Token 已失效；立即把新 Token 同步到管理系统并重做连接验证。不要为了方便而长期保存或展示明文 Token。

**状态：** 2026-09-15 文档记录了问题和改进方案；当前版本是否已改按钮及连接流程，需在现有页面复核。

### 4. 构建环境版本不匹配

**什么情况下：** 销售系统构建无法通过，机器上是 Node 24，而项目要求 Node 20；pnpm 同时因 npm registry EACCES 无法获取依赖。

**出了什么问题：** 环境版本不符合项目约束，且依赖网络/权限不通；这不能证明业务代码有问题，也不能作为构建通过的依据。

**解决办法：** 在 Node 20.x 和项目指定 pnpm 版本的环境中，使用锁文件安装依赖；使用可访问 registry 或准备离线缓存后重新执行构建和 lint。该记录来自 2026-09-15，当前状态应重新核对。

## 七、Git 分支和未提交内容

### 1. 直接把工作分支合入 dev_l 出现大量冲突

**什么情况下：** 将 codex/multi-tenant 合到 dev_l 时，多个文件出现 add/add 和 content conflict。

**出了什么问题：** 两条分支的文件树差异较大；当时工作区还存在 README、Logto 文档、部署脚本的未提交修改和生成的未跟踪 JSON 文件。普通 git stash 不会收集未跟踪文件。

**当时怎么处理：** 中止冲突合并，先用包含未跟踪文件的 stash 保全本地改动；已提交内容留在原分支，随后按用户的“覆盖提交到 dev_l”要求建立覆盖树提交并推送。历史中 f489111 是覆盖提交。Stash 仍是本地恢复点，不会随远端分支一起推送。

**后续避免踩坑：**

1. 切分支前看 git status，区分已提交、已修改、未跟踪文件。
2. 要临时保全未跟踪内容时，确认 stash 包含 untracked；重要改动优先单独 commit 或备份分支。
3. 先看分支图、共同祖先、双方提交和文件树差异，再决定 merge、cherry-pick 或按要求覆盖。
4. “切到某分支”不等于“把当前代码合入该分支”；覆盖推送是不同操作，执行前要核对目标分支和目标树。
5. 操作后再检查工作区、分支指向、远端和 stash 清单；不要把 stash 当成远端备份。

## 八、项目部署脚本和迁移的边界

- Logto 一键脚本可用于首次配置和已部署后的重复更新；默认是普通运行，只有加 -Dev 才启用开发热重载。仅配置不启动容器使用 -ConfigureOnly。
- M2M Secret 每次按需输入，不应写入仓库文件；生成的演示密码、迁移 manifest 和本机配置也应留在忽略文件内。
- Logto migration 不迁移 lxScope Redis/PostgreSQL 业务数据、不导出密码。跨租户会变更用户/组织 ID，必须先生成身份映射，再规划业务数据的 ID 改写。
- LOGTO_ENDPOINT、浏览器 VITE_LOGTO_ENDPOINT、后端内部 JWKS 地址和 Management API 地址用途不同；不要为了“容器能访问”而改错 issuer。

## 九、当前仍需明确复验的项目

1. **MCP 生命周期与分配：** 页面切换、后端 reload、容器重启后的 stateful MCP 连续恢复；全体/指定用户分配是否实际落库并对目标用户可见。
2. **销售总台连接：** 当前两套 Compose 的网络、端口、总部地址和内部地址；页面是否显示业务错误码；Token 按钮是否仍会轮换。
3. **Logto 实际前端实例：** 当前浏览器访问的是哪一个端口和 Compose project；SPA App ID、offline_access、回调地址是否与运行中的构建产物一致。
4. **知识图谱业务质量：** 用脱敏业务材料复核实体合并、关系方向、别名、来源位置和大文档性能。
5. **销售系统构建：** 用符合 Node 20 约束的环境重新确认 build/lint；旧记录不能代表当前构建状态。
6. **分支保全：** 需要清理 stash、生成配置或覆盖历史前，先查看它们目前是否仍包含唯一副本；远端分支不能代替本地 stash。

## 十、遇到问题时的快速排查顺序

1. 记录用户当前访问的 URL、端口、时间和操作步骤。
2. 找到实际运行的容器/进程，确认 Compose project、网络、端口映射和读取的 env 文件。
3. 将故障定位到具体阶段：浏览器登录、Logto Token 签发、后端鉴权、数据库查询、MCP 连接、工具执行或前端展示。
4. 对照响应体和日志里的业务错误，不要只根据 HTTP 200/403 或 UI 徽标下结论。
5. 核对外部服务配置与运行实例，而不是只看代码中的默认值。
6. 任何分支切换、重启、清理和覆盖前先保全当前状态；操作后确认目标实例和目标分支。
