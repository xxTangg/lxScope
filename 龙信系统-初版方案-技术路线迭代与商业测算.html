龙信系统 · 今日初版方案

先把路线拉齐，再让每次迭代被看见，最后把账算明白。

这不是一份单纯的技术差距报告，而是一份可以直接拿来对齐产品、技术和商业思路的初版方案。

核心承诺：用户今天能看到变化，团队每天能交付结果，管理者能随时知道成本、并发和任务上限。
第一屏先对齐三件事

从“能不能做”转向“用户能不能感知、公司能不能算清”

1

技术路线合并

以现有 lxScope/AgentScope 能力为基线，不推倒重来，补齐龙信的企业产品层。

  • 复用 Agent、会话、知识库、权限和 Pipeline 底座
  • 增加安全模式、租户边界、工作流和运营后台
  • 形成长期可维护的“底座 + 产品层”结构
2

功能迭代显性化

不等“大版本”才让用户看到变化，每天都有可展示、可验证、可复盘的输出。

  • 每天一个可感知的功能或体验改进
  • 每周一个可演示的稳定闭环
  • 每次迭代都有截图、指标和验收场景
3

商业模式测算

建立一本关于 Token、算力、并发和任务额度的账，先把成本和上限算明白。

  • 一个任务平均消耗多少 Token
  • 当前算力支持多少并发和每日任务
  • 普通会员账号能够稳定完成多少任务
路线合并方案

不换底座，补齐三层产品能力

当前项目已经有 Agent 平台底座，龙信下一阶段的重点不是再堆工具，而是把安全、工作流、运营和商业账本接到同一条产品路线中。

现有底座
Agent 运行层 会话、消息流、任务中断、知识库、MCP、Skill、Pipeline、人工确认
下一阶段
龙信产品层 安全模式、租户隔离、Office 工作流、结果页、版本发布、管理员控制台
最终形成
企业经营层 Token 账本、套餐额度、并发控制、运营数据、审计和可恢复运维
路线原则：先基线拉齐，再高频交付；先把边界管住，再扩大 Agent 自主能力；先做一个真实工作流，再扩展通用 BPMN。
现状与差距

当前系统已经有什么，还缺什么

能力当前 lxScope与龙信目标的关系
Agent 与会话有 Session、SSE、状态、停止、中断、任务工具和人工确认底座已有
知识库支持 PDF、Word、Excel、PPT、图片解析和向量检索基本已有
账号体系有 JWT 登录、注册、当前用户和 Token 汇总基础已有，企业管理缺失
Office 输出有工作区和下载能力，有 Office 依赖，但缺少固定模板生成闭环需要产品化
权限安全有权限引擎和 HITL，但默认使用本地工作区，并默认挂载浏览器 MCP与企业安全基线有冲突
工作流有 GoalPipeline、重试、任务和人工确认有底座，缺工作流中心
计费与 HQ没有套餐、余额、订单、充值、额度、总部和账本模型基本缺失
审计与恢复支持本地卷备份和离线镜像，但缺少异地恢复和完整审计需要补齐
关键提醒：当前服务默认启用 Playwright 浏览器 MCP，且示例部署使用 LocalWorkspaceManager。这与龙信文档要求的“默认关闭网络、主机读写和命令能力”不一致，应先建立企业安全模式。
让用户每天感知变化

高频迭代不是“每天发代码”，而是每天交付一个可验证结果

DAY 1
安全模式开关用户能看到企业模式与开发模式的边界。
DAY 2
任务成本展示用户能看到本次任务 Token 和估算成本。
DAY 3
结果文件关联用户能从一条消息直接找到生成结果。
DAY 4
人工确认节点用户能暂停、确认、退回并继续任务。

每日输出标准

  • ✓一个用户看得见的界面或流程变化
  • ✓一个可重复的验收场景
  • ✓一张截图或一段演示结果
  • ✓一项指标：成功率、耗时、Token 或并发

每周稳定闭环

以“上传资料 → 生成内容 → 人工确认 → 导出文件 → 查看成本”为一条主线，每周完成一个能让用户真正使用的闭环。

用户感知目标：用户不需要了解底层 Agent，也能感觉到系统越来越快、越来越稳、越来越会办事。

今天给出的初版优先级

先做三件事，形成可感知、可维护、可经营的系统

P0
企业安全模式与租户隔离
关闭默认浏览器/网络/主机命令，统一 JWT，补齐组织、角色、资源边界、审计和安全验收。
先把边界管住
P0
数据可靠性、Token 账本和恢复机制
把任务、Token、文件、Qdrant、Redis 的数据链路记录清楚，完成备份、恢复和 RPO/RTO 验证。
先把账算清楚
P1
PPT/Word 工作流垂直闭环
先做一套 PPT 和一套 Word 流程，支持上传、生成、人工确认、退回、重试、导出和结果关联。
先做出用户能用的结果
P1
企业管理和运营控制台
增加用户、角色、套餐、额度、并发、用量账本、审计、版本发布和升级回滚。
让系统可经营
P2
高级 Office、OCR、引用和通用 BPMN
在安全、可靠性和垂直工作流稳定后，再扩展复杂排版、引用定位、并行节点和受控联网搜索。
扩展上限
建议的下一步

把“探索思考”变成下周可以验收的结果

第一周：拉齐基线

  • 确定企业安全模式的默认工具清单
  • 采样 100 个真实任务，建立 Token/耗时/失败账本
  • 完成跨用户和跨租户访问验收
  • 确定 PPT/Word 第一条业务流程

第二周：交付首个用户闭环

  • 任务结果页和 Token 成本展示
  • 一个可暂停、确认、退回、重试的 Office 流程
  • 每日输出截图、演示和指标
  • 形成第一版会员额度和算力测算表
最终判断：当前项目不需要推倒重来。最合理的路线是复用已有 Agent 底座，优先补齐安全、可靠、工作流和商业账本，让系统从“能运行”走向“用户能感知、团队能维护、公司能经营”。
